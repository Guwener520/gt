01导读：三分钟建立坐标系

30 秒读懂

前两篇分别定义了"考什么"（SWE-bench）和"怎么交互"（SWE-agent）。OpenHands 问的是第三个问题：这些东西怎么才能被别人复用？它把智能体拆成三层——策略（agent）、状态（事件流）、执行（Docker 沙箱），三者通过一个只追加的事件流串起来。结果是：换 agent 不用改沙箱，换模型不用改评测，同一份轨迹同时供下一轮提示词、前端界面和打分脚本使用。

它的定位是基础设施而非方法：32K GitHub star、188 位贡献者、2.1K 次提交（原文 p.3），15 个基准（原文 p.6）。对本课题最有用的一点：它的"事件流"就是"统一事件表示"的工业级版本，而它缺的那一层——把事件按"任务"组织起来——正是本课题要补的。

阅读建议

正文重点读 §2.1（状态与事件流）、§2.3（AgentSkills 收录标准）、§4（评测）。表 1 是框架对比清单，看结论前先想清楚它比的是什么。附录 D 讲 UI 怎么接事件流，附录 E 讲怎么给智能体写集成测试，做系统时比正文更有用。

02它要解决什么问题

2023—2024 年的代码智能体论文几乎每篇都自带一套脚手架：自己的提示词、自己的工具函数、自己的日志格式、自己的评测脚本。后果是三个：换一个模型要重写一遍；两个人报的同一个基准分数不可比，因为工具集与截断策略都不同；轨迹只被当成调试日志，跑完就丢，谁也没法拿它做二次分析。

所以问题不是"再做一个更强的 agent"，而是"能不能让 agent 变成可替换的零件"。

论文式实现

  • agent 与执行环境耦合，换沙箱要改 agent
  • 轨迹打印到 stdout，格式各写各的
  • 评测脚本绑死某个 agent 的接口
  • 人无法中途介入

平台式实现

  • 三层分离：策略 / 状态 / 执行（原文 p.3—p.4）
  • 状态是显式事件流，可回放、可序列化
  • 同一套评测跑 15 个基准（原文 p.6）
  • 用户可随时打断并补充指令（原文 p.6）
打个比方

不是造一台更快的车，而是先定标准集装箱的尺寸。集装箱定下来之后，港口、货轮、卡车才能各自升级——平台的价值在于让别人不必重复造轮子。

03核心思想：三层分离与一份事件流

一句话：把智能体系统拆成"策略 / 状态 / 执行"三层，让三层之间只通过一个只追加的事件流通信。原文的定义很干脆——状态（state）封装了 agent 执行所需的全部信息，其核心是事件流：过去所有动作与观察的按时间排列的集合，既包括 agent 自己的动作，也包括用户的指令与反馈；状态里还附带累计的 LLM 调用成本与多智能体委派元数据（原文 p.3）。

关键机制

① 策略与执行分离，才能各自演进。agent 只实现 reset() 与 step(state)（原文 p.4 图 3 的 MinimalAgent 只有这两件事），执行细节全在 runtime 里。所以换一个 agent 不需要动沙箱，换一个沙箱不需要动 agent。

② 状态显式化，才能一份数据三用。事件流是"过去动作与观察的按时间排列的集合"（原文 p.3）；因为它是显式数据结构，前端可直接订阅（原文 p.19）、评测可读、下一轮提示词可从它派生。若轨迹只是日志字符串，这三件事要各写一遍。

③ 沙箱隔离，才能让"执行任意代码"成为可接受的风险。每个任务会话起一个隔离容器，动作在容器里执行、结果回到事件流（原文 p.4）；还支持任意基础镜像（原文 p.5）。

④ 委派也是一条事件，多智能体就不用改框架。AgentDelegateAction 让 agent 把子任务交给另一个 agent（原文 p.5），委派关系记在 state 元数据里。

04方法拆解：四个部件

  1. Agent 抽象　输入是 state，输出是一个 action。约定极简：reset() 初始化，step(state) 产出下一步动作（原文 p.4 图 3）。AgentHub 里已有 CodeActAgent（默认）、Browsing Agent、GPTSwarm、Micro Agent 等实现（原文 p.6）。
  2. 事件流与动作类型　核心动作只有三类：IPythonRunCellAction（跑 Python）、CmdRunAction（跑 bash）、BrowseInteractiveAction（操作浏览器），外加 AgentDelegateAction（委派）。选"编程语言作为动作空间"是因为它足够通用又能自我扩展（原文 p.3—p.4）。
  3. Runtime 与沙箱　每个任务会话起一个 Docker 容器，容器里跑一个 API server 监听动作执行请求，执行完把结果写回事件流；客户端通过 REST 通信（原文 p.4）。支持任意基础镜像，因此可以复现各种软件环境（原文 p.5）。
  4. AgentSkills　一个 Python 包，函数自动导入 IPython 环境，所以定义一个工具就是写一个函数。收录标准只有两条：模型自己写代码搞不定，或者需要调用外部模型（原文 p.5）。已有的 edit_file、scroll_up 等来自 SWE-agent 与 Aider 的改造（原文 p.5）。

这四块里最值得学的是第 4 条的收录标准。多数工具库的直觉是"能包就包"，这篇反过来：模型已经会用 pandas 读 CSV，就不要造一个"读 CSV 工具"。这条标准背后是一个判断——工具库的成本不是代码量，而是它占用的上下文与选择成本。这与第 02 篇 SWE-agent 的"命令少而专"是同一个道理的两种说法。

05实验与结果：广度证明，不是能力证明

设置：把 15 个已有基准接进同一套框架，用同一批 agent 实现跑（原文 p.6）。主结果见表 2。成本：跑完整 2,294 条约 6.9 千美元（每条 3 美元估），Lite 300 条约 600 美元（原文 p.7、p.19）。

三个读法。一，它没有刷榜。SWE-bench Lite 上 26.0 低于 Agentless 的 27.3，也低于 Moatless 的 26.7（原文 p.7）；作者自己也写"可能并非每个类别都达到最好"（原文 p.7）。这不是掩饰——平台论文的目标本来就不是单点最高分。二，同一个 CodeAct agent 不改系统提示词就跨了三类任务（22.0 / 14.5 / 53.1，原文 p.7），这才是它想证明的东西：接口足够通用。三，横向比较要小心口径。HumanEvalFix 上 OpenHands 是 79.3%（0-shot），SWE-agent 是 87.7%，但后者给了 1-shot 的完整示范轨迹（原文 p.7），两者不能直接比大小。

还有一处易被误读：表 1 里 OpenHands 是唯一全勾的（原文 p.6），但那是按功能清单自评的表，不是实验——说明"功能齐"，不说明"效果强"。把它当"能力证据"引用，会被答辩老师抓住。

06局限与可质疑之处

  • 作者自述：多模态支持还不是有原则的设计；agent 仍难以完成复杂任务；长文件编辑效果差；工作流仍需大量手工搭建（原文 p.17—p.18）。
  • 外部质疑：15 个基准每个都只跑一两个 agent、报一个数，深度不足；表 1 的自评清单容易被当成实验证据；分数落后于专用方法时，"通用性"是解释而非证据。
  • 我的判断：

一、平台论文的正确评测标准是可复现性，不是分数。它真正交付的是"别人能在你的基础上重跑并比较"。可惜论文没量化这一点（比如"第三方复现某篇论文，误差多少"），只在附录 E 讲了怎么给智能体写集成测试（原文 p.19）。这是平台类工作普遍缺的一块。

二、事件流是扁平的，没有"任务"这一层。state 里只有时间序事件、成本、委派元数据（原文 p.3）。这对"跑一个任务"够用，但对本课题关心的"多个并行任务、中断后恢复、按任务查证据"不够——时间序里没有任务边界，也没有"这条事件属于哪个任务"的字段。这不是实现疏漏，而是目标不同：它服务的是"跑通并评测"，我们服务的是"回看并追溯"。

三、安全只覆盖了"宿主隔离"。伦理部分的三条缓解措施是系统评测、人机协作、前沿安全研究（原文 p.18）；沙箱解决了"会不会弄坏我的机器"，没解决"轨迹里会不会留下不该留的密钥与隐私"。采集端照抄它的存储方式，会把这个问题一起抄进来。

07与本课题的关系

怎么用

开题报告「二、2（三）系统总体架构」的四层划分可以直接对标本篇的三层：它的 Runtime 对应采集端，Event Stream 对应事件存储，Agent 对应被观测对象。更重要的是「二、2（四）关键设计」里写了"事件 JSON 参考 OpenTelemetry GenAI 语义约定"——本篇的事件流就是现成的参照物，可以引它来说明"为什么事件要按动作/观察成对记录、为什么要带成本与委派信息"。

可借鉴

事件流的字段组织方式。研究内容（1）可照它的思路：一条事件 = 类型 + 动作载荷 + 观察载荷 + 时间戳 + 成本 + 归属。再加 taskId 与 hunkId 两个字段，就把扁平时间序升级成了任务视图——这是本课题的核心增量。

要避开

不要把"功能清单"当创新点。表 1 那种"我全都有"的对比在开题报告里说服力很低。创新点应落在"事件 → 任务"的组织方法与双向溯源查询上，而不是"我们也做了时间线界面"。

不能支撑

它没有反向查询。事件流支持"从事件往下看"，但"从代码反查为什么被改"需要 diff 坐标到事件的反向索引，本篇没有。它也没有任务续接：中断后靠把整条历史重新喂给模型，而不是"进展摘要 + 未完成项"。

对应到哪个模块。研究内容（2）可照它的 runtime 设计——"动作在隔离环境执行、结果写回事件流"是最干净的分层；研究内容（3）需要它的动作—观察配对作骨架，但要补"哪个 hunk 由哪次动作产生"的映射；研究内容（4）的时间线视图几乎就是它前端订阅事件流的做法，任务中心与证据侧栏才是要新建的。

这个状态的核心组件是事件流——过去所有动作与观察按时间排列的集合，既包括智能体自己的动作，也包括用户的交互。

我们只在两种情况下新增一个技能：模型自己写代码不容易做到，或者它需要调用外部模型。

09术语表

事件流 event stream
按时间排列、只追加的动作与观察序列，外加用户消息。它是 agent 状态的主体，也是前端与评测的共同数据源。
状态 state
事件流 + 累计成本 + 多智能体委派元数据 + 执行参数（原文 p.3）。
运行时 runtime
执行动作的一侧：每会话一个 Docker 沙箱 + 容器内 API server + REST 客户端。
AgentHub
社区贡献的 agent 实现集合，可作基线也可直接使用（原文 p.6）。
AgentSkills
工具库。收录标准只有两条，核心是"模型能自己写代码搞定的就不包"。
委派 delegation
用 AgentDelegateAction 把子任务交给另一个 agent，如把浏览任务交给 BrowsingAgent（原文 p.5）。
Micro Agent
复用通用 agent 大部分实现、只换提示词的专用 agent，用来降低社区贡献门槛（原文 p.6）。

10带着问题重读

如果只允许从这篇里拿一个设计，你拿什么？

事件流作为唯一状态源：提示词从事件派生、界面订阅事件、评测读事件。本课题的"统一事件表示"可直接采用这个立场，只是要在事件上挂任务归属。

为什么它的分数不是最高的，却最有影响力？

因为它降低了别人的成本。专用方法（Agentless、Moatless）单点更强，但你没法在它们之上做新实验；它提供的是"能改的底座"。影响力与分数不在同一个坐标系。

事件流能直接拿来当"变更溯源"的数据模型吗？

不能直接。它记录"发生了什么动作"，而溯源要回答"这段代码为什么变成这样"——需要把动作映射到 hunk、把 hunk 映射到触发它的消息与验证它的测试。这三次映射正是研究内容（1）（3）要做的。

它的成本数据对本科课题有什么参考价值？

有：600 美元跑一次 Lite（原文 p.19）说明"评测本身要花钱"。本课题用 6—8 个任务、4—5 名受试者，规模小得多，但同样应预算并记录 LLM 成本，否则"可复现"是空话。
