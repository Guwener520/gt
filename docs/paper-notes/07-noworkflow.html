01导读：三分钟建立坐标系

30 秒读懂

你写了个 Python 脚本跑实验，前后跑了十几遍。某一天发现第 13 遍的图和第 4 遍的不一样，可你记不清当时改了哪一行、装了哪个版本的 numpy、那个输入文件有没有被别的脚本覆盖过。git 只能告诉你"代码文本变成了什么"，答不了"这一次执行为什么产生这个结果"。noWorkflow 的解决办法极轻：把 python experiment.py 换成 now run experiment.py，脚本一行不用改，它就把这次执行涉及的定义（脚本结构）、部署（环境与库版本）、执行（函数激活、变量、文件读写）三层溯源全部记下来，存进脚本目录下的 .noworkflow，之后可以用 SQL、Prolog 或网页界面事后追问、跨次比较，甚至把某一次执行的文件状态整个还原（原文 p.1–p.3）。

要理解它站在哪儿，得先看它出现之前溯源领域的两条老路。第一条是操作系统级溯源（如 Provenance-Aware Storage Systems、BUrrIto）：通用、语言无关、完全自动，但采到的信息"难以推理、难以对上实验本身的语义"（原文 p.1）。第二条是工作流管理系统（WFMS，如 VisTrails）：科学家先把自己的实验写成工作流，溯源就天然贴合实验语义，代价是学习曲线陡、采纳成本高、失去通用语言的灵活性——所以"很多科学家仍然在用脚本"（原文 p.1）。noWorkflow 选的是中间那条缝：保留脚本的自由，但把"执行"提升为一等公民。它上承 PROV 一脉的溯源传统，往下被同一课题组继续扩展到交互式 notebook，并与 YesWorkflow 联动把"预期溯源"和"回顾溯源"接起来（原文 p.1）。对本课题而言，它是"无侵入采集 + 事后可查询"这条技术路线最干净的一个样板。

阅读建议

这是 4 页的演示（demo）论文，不要按"方法论文"的读法找实验章节——它没有。正确顺序：先看第 2 页的 Figure 1（三层架构），再顺着第 3 节的降水数据演示读一遍，你会看到 trial 编号、dataflow 图、activation 图、diff、restore 依次出场；最后回到第 4 页的结论看它自己承认没采什么。第 4 页后半是参考文献，可以跳过。

02它要解决什么问题

想象一个真实场景：研究者接到合作者请求，要验证"里约热内卢的降水量是否逐年稳定"。她从气象数据库取数据，写了脚本读 p13.dat 与 p14.dat，按月求和，画柱状图存成 out.png（原文 p.2，Figure 2）。这个脚本会跑很多遍：加 2012 年的数据、剔除异常雨天重跑、换成 2015 年的数据再跑。麻烦不在写代码，而在于事后无法重建"那一次"——哪次用了哪些输入、当时 matplotlib 是 2.0.0 还是别的版本、图里那根柱子为什么比记忆里高。

原文把这件事的难点拆得很清楚（p.2）：第一，粒度难选，粗粒度会藏掉关键数据，细粒度会淹没用户；第二，脚本里有控制流和循环，"究竟是脚本的哪一部分贡献了这个数据产物"并不显然；第三，脚本跑在不受控的环境里，光看结果无法区分是代码变了还是环境变了。而当时已有的脚本级溯源工具，多数只针对单次执行（single trial），于是它们采集不到检验可重复性所需的信息、不支持数据复用、也管不了实验的演化（原文 p.1）。这句话是整篇论文的靶心。

之前的做法

  • OS 级溯源：全自动、语言无关，但语义对不上实验意图
  • 工作流系统：语义精确，但要重写实验、学习成本高
  • 脚本级工具：多数只记一次执行，无法比较、无法复用、无法管演化
  • 版本控制：只记代码文本的差异，不记环境与执行

这篇的做法

  • 三类溯源一起采：定义、部署、执行
  • 以 trial（一次执行）为版本单位，可 diff、可 restore
  • 内容按 SHA1 寻址，同一内容只存一份
  • 事后可查询：SQL、Prolog 传递闭包、图形化 dataflow / activation
打个比方

git 像病历上写的"诊断结论"——它忠实记录处方被改成了什么，但不会记录这次手术是怎么做的、用了哪一批批号的药、术中血压是多少。noWorkflow 补的是后者：一台全程录像机加一份术中清单。两者不冲突，只是回答的问题不同：git 回答"代码现在长什么样"，noWorkflow 回答"这次结果是怎么来的"。这也是为什么原文最后要专门说一句"与标准版本控制系统不同，noWorkflow 的版本关联的是 trial 执行"（原文 p.4）。

03核心思想：一句话与一张图

一句话：用静态分析给源码里的每个可执行位置发一个"身份证"，再用运行时探针把发生的事挂到这些身份证上，全部按内容哈希存进本地库，于是"事后追问"变成在同一张图上的遍历。

关键机制

为什么这样设计就 work？拆成四个因果环节看，每一环都在补上一个环留下的坑。

① 静态锚点让运行时事件"有地方可挂"。运行时日志天然只有时间戳和值，没有语义位置。noWorkflow 先分析 AST 与字节码（原文 p.2），把函数定义、调用、参数这些结构固定下来，运行时发生的激活才有一个稳定的落点。这是"能查"的前提——否则你只能得到一串流水。

② 内容寻址让"跨次比较"变廉价。所有被访问的文件、模块、脚本都按内容的 SHA1 复制进内容库，哈希同时充当关系库里的外键（原文 p.2）。同一份内容只存一次，于是"两次 trial 的输入是否相同"退化成"两个哈希是否相等"，diff 和 restore 才不需要重算整个工作目录。

③ 以 trial 为版本单位，让演化有了坐标系。版本控制的版本单位是"人主动提交的代码状态"，而实验的因果单位是"一次执行"。换成 trial 之后，diff（比较两次执行）、restore（回到某次执行前的文件状态）、history（trial 之间的派生关系）三个操作都落在同一个数据模型上，不需要额外的机制（原文 p.3–p.4）。

④ 粒度可调，把"记全"与"能用"的矛盾变成旋钮。默认用 Profiler 采函数激活、全局变量、参数与返回值；要更细就 now run -e Tracker，额外记变量赋值与变量依赖（原文 p.2–p.3）。这就承认了一个事实：溯源没有"最优粒度"，只有"针对某个问题的合适粒度"。

04方法拆解：它到底怎么做的

按原文第 2–3 节的真实结构，它是四个部件串起来的：

  1. 入口：now run 分配 trial 编号输入是一个完全不需要修改的 Python 脚本；动作是替换解释器入口，先分配一个顺序递增的 trial 编号，再依次采集定义溯源、部署溯源，最后执行脚本并采集执行溯源；输出是磁盘上 .noworkflow 目录里的一次完整记录（原文 p.2）。原文特别强调它能"运行完全相同的脚本并产生相同结果"，这是"无侵入"最硬的证据。
  2. 采集：三类溯源用三套技术定义溯源靠 AST 与字节码分析，脚本文件与函数定义进内容库，函数名、调用、参数、全局变量进关系库；部署溯源靠 os、socket、platform、modulefinder 采操作系统、主机名、架构、Python 版本、环境变量，以及库依赖的传递闭包及其版本；执行溯源靠 Profiler（默认）或 Profiler 加 Tracer（细粒度），并在读写文件前后各复制一份文件内容进内容库（原文 p.2）。
  3. 存储：一个目录两个库结构化数据进关系库，文件类数据进内容库，二者用 SHA1 哈希串起来，同时避免相同文件重复存储（原文 p.2）。这个设计很小，但决定了后面所有查询能不能写成一句 SQL。
  4. 分析：把数据翻译成五种看法命令行文本视图（now show）、dataflow 图（now dataflow 1，导出 dot 再渲染）、activation 图（节点是激活，颜色按耗时渐变，红最慢白最快）、trial 间 diff（now diff 1 2）、以及 restore 与 history（now restore 1 会先造一个 backup trial 再还原文件）（原文 p.3–p.4）。

值得单独讲的细节：查询为什么需要 Prolog

既然数据在关系库里，为什么还要导出成 Prolog 事实？原文给的理由很具体：复杂查询需要传递闭包，而部分数据库系统对递归查询的支持有限（原文 p.3）。于是它把 trial 的溯源导出成 Prolog 事实，并可选导出预定义规则。论文举的例子是 access_influence(1, File, 'out.png')——"trial 1 里哪些文件可能影响了 out.png 的生成"，答案回到 p13.dat 与 p14.dat（原文 p.3）。这正是"证据链"最原始的形态：从一个产物反向走到它的输入，而且这个"走"是自动的、可重复的。

容易误读

别把它读成"一个更聪明的日志工具"。日志是写给人看的顺序流水，读完就完了；noWorkflow 产出的是可被查询的图结构——同一个数据集既能渲染成 dataflow 图，也能被 SQL 过滤、被 Prolog 递归遍历。这个差别决定了它能不能回答"为什么"，而不只是"发生了什么"。另一个常见误读是把它当成 git 的替代品：它不记录分支与合并，也不管多人协作，它只关心单机上一次次的执行。

这三个动作分别对应"可比较""可重放""可解释演化"。它们不是性能提升，而是能力的有无——在没有这类工具时，这三件事只能靠人记笔记。至于开销，必须诚实说：原文没有给出任何采集开销的量化数据，只在 p.3 定性承认"细粒度采集或大循环会让溯源体积显著增长"，并给出三个减量旋钮：限制采集栈的最大深度、把计算密集的函数挪到外部文件（默认只采主脚本的执行溯源）、给变量或函数名加下划线前缀表示不采（原文 p.3）。如果你要在论文里写"noWorkflow 的开销是多少"，这里没有可引的数字。

06局限与可质疑之处

分三层看，越往后越是我自己的判断。

  • 作者自述：它不直接采集网络活动与数据库访问，只记录为此调用的函数（原文 p.4）；细粒度采集会让数据量显著增长，只能靠三个旋钮压（p.3）；此外它明确是 Python 专用，且默认只采主脚本的执行溯源。
  • 外部质疑（体裁层面）：演示论文没有评估章节，也没有用户研究。它在 4 页里证明的是"这件事能做成、做出来长这样"，而不是"它比别的方式更好"。同一课题组的后续工作（notebook 扩展、与 YesWorkflow 的联动）才是逐步补证据的地方——引用时必须把这条界线画清楚，否则就是把设计主张当成有效性证据。
  • 我的判断一：粒度选错了场景就是负资产。它默认采到"变量赋值与变量依赖"这一级（p.3），这在科学计算里合理，因为变量就是实验的中间产物。但本课题的对象是代码智能体的会话：代码在沙箱里被执行，你能拿到的稳定证据是工具调用、文件快照与测试结果，变量值既拿不到也不重要。照搬变量级溯源会得到一个采集不到、存不下、也没人查的字段。
  • 我的判断二：可迁移的是数据模型，不是采集技术。AST 变换要求"能拿到源码、且是 Python、且在同一个解释器里跑"，这三条在智能体场景一条都不成立（模型可能整文件重写、可能是 TypeScript、跑在容器里）。真正能搬过来的是它那套把"产物—活动—输入"组织成可遍历图的思路，以及"内容哈希当主键"这个工程决定。
  • 我的判断三：内容寻址的代价被轻轻带过了。每个 trial 都存被访问文件的副本，磁盘占用随 trial 数线性增长；去重只在"内容完全相同"时生效，而实验里最常发生的恰恰是"内容改了一点点"。原文只说"可能显著增长"（p.3），没给增长曲线，也没给清理策略。真要用在长期运行的环境里，这是必须先回答的工程问题。

07与本课题的关系

怎么用

引在哪：开题报告"一、2（三）过程溯源与证据链"已经把它作为"把脚本执行捕获为可查询溯源图"的代表引作 [35]，可以直接沿用；"二、1（三）研究内容（4）变更溯源与证据链"在讲 hunk 粒度的证据链时，可以引它来说明"证据链不是本课题首创，但对象与粒度不同"。对应哪个模块：研究内容第 ③ 块"变更溯源与证据链"里的变更卡片，本质是它 access_influence 查询的 hunk 版——把"哪些文件影响了这个产物"换成"哪条指令、哪次工具调用、哪次测试运行支撑了这个 hunk"；研究内容第 ④ 块"任务快照与任务续接"里的检查点（Checkpoint），与它的 trial / restore / history 是同构的。

本篇对应的是四个核心问题里的溯源断裂：从一段代码反查它的触发来源与验证依据。同簇另两篇各补一角——MSR 综述给出"数据源分散、跨源无链接"的问题地图（对应信息分散），中断恢复研究给出"上下文丢失有多贵"的实证（对应上下文丢失）。三篇合起来，正好是本课题四个核心问题中三个的文献底座。

可借鉴

"以执行/任务为版本单位"这个决定。它把 diff、restore、history 三个操作统一在一个数据模型上；本课题用 Task 代替 trial，就能让"任务时间线""任务快照""任务续接"共享同一套查询。

可对照

它的三层溯源（定义/部署/执行）可以当作本课题事件模型的完备性检查表：本课题的八类实体里，"部署"这一层几乎空缺——只记了工具调用，没记运行环境与依赖版本。这是一个可以在论文里如实写出的设计取舍。

要避开

不要照搬 AST 变换做采集，也不要把"变量级溯源"写进需求。本课题的采集端是黑盒事件流，能保证的是"事件 + 快照 + 哈希"，不是解释器内部的变量状态。

它不能支撑什么：第一，不能支撑"证据链能提升开发者理解或缩短恢复时间"——它没有任何用户研究，这个结论必须由本课题自己的 M7/M8 实验给出。第二，不能支撑跨工具、跨语言、跨进程的采集，它连 Python 之外的脚本都不管。第三，不能支撑"用大模型生成摘要并绑定证据"，它没有 LLM 环节，其"可查询"是人写 SQL 或 Prolog 去查的，与本课题"模型自动生成、结论须可回溯"是两种不同的可信性策略。第四，不能支撑"任务边界判定"——它的 trial 边界由"用户执行了一次 now run"这个动作显式给定，而本课题的 Task 边界恰恰是待判定的问题（RQ5）。换句话说：它替本课题解决了"记下来之后怎么问"，没解决"怎么记才不用改代码"和"边界在哪里"。

noWorkflow 能运行完全相同的 Python 脚本并产生相同的结果，无需任何修改。

— 原文 p.2

Provenance size may grow considerably if it is captured at a fine granularity or even at a coarse granularity, if script contains large loops.

若以细粒度采集，甚至在脚本含大循环时以粗粒度采集，溯源体积都可能显著增长。

— 原文 p.3

Different from standard version control systems, noWorkflow versions are related to trial executions.

与标准版本控制系统不同，noWorkflow 的版本关联的是试验执行。

— 原文 p.4

09术语表

试验 trial
实验脚本的一次完整执行。noWorkflow 用它当版本单位，编号从 1 递增；本课题里与之最接近的概念是"开发任务"的一次执行轮次。
定义溯源 definition provenance
脚本的静态结构：函数定义、调用、参数、全局变量。相当于"程序长什么样"的权威版本。
部署溯源 deployment provenance
执行环境：操作系统、主机、架构、解释器版本、环境变量、库依赖的传递闭包及其版本。它让"结果变了"能区分是代码问题还是环境问题。
执行溯源 execution provenance
运行时的执行日志：函数激活、参数、返回值、变量赋值、文件读写。粒度由采集方式决定。
激活 activation
一次函数调用的执行实例。activation 图里一个节点就是一次激活，节点颜色按耗时从白到红渐变（原文 p.3）。
内容寻址 content addressing
按内容的 SHA1 给文件命名并存储，同一内容只存一份。哈希同时充当关系库里的外键，是跨 trial 比较的基础。
预期溯源与回顾溯源 prospective / retrospective provenance
前者是"打算怎么做"（工作流定义），后者是"实际怎么做的"（执行记录）。原文提到 YesWorkflow 与 noWorkflow 的联动正是把两者接起来（p.1）。
传递闭包查询 transitive closure query
"沿着依赖关系一直往上追"的查询，例如"哪些输入最终影响了这个产物"。原文因此把溯源导出为 Prolog 事实（p.3）。
还原 restore
把工作目录恢复到某次 trial 执行前的文件状态；因当前代码已被修改，命令会先创建一个 backup trial 保留现场（p.3）。

10带着问题重读

为什么它要把"版本"的单位定为一次执行，而不是一次代码提交？如果改成提交，会丢掉什么？

提示：回到 p.1 对"单次试验工具"的批评和 p.4 对 git 的区分。一次提交可以对应多次执行（同代码跑不同输入），一次执行也可能跨多次提交（边改边跑）。以提交为单位就丢了"输入与环境的差异"，而这恰恰是实验结果变化的另一半原因。

原文说细粒度会"淹没用户"，它给的三个减量旋钮各自牺牲了什么？

提示：p.3 的三条——限制栈深度、把重计算函数挪到外部文件、下划线前缀。第一条丢的是深层调用的证据；第二条丢的是被挪走那部分代码的执行溯源（默认只采主脚本）；第三条把"该不该记"的判断交给了写代码的人，等于把负担转移给用户。

如果要把它的思路用到代码智能体上，哪一层能照搬，哪一层必须换掉？

提示：数据模型（产物—活动—输入 + 内容哈希）可以照搬，因为它是通用的；采集技术（AST 变换 + 解释器探针）必须换，因为智能体场景拿不到解释器内部状态。换掉之后要重新回答一个问题：新的"锚点"是什么？（本课题的答案是 hunk 的内容哈希加文件路径。）

这篇没有评估，你凭什么说它"work"？

提示：看 p.3–p.4 的演示是否闭环——从采集（三层溯源都落库）、到查询（SQL/Prolog 各自给出答案）、到操作（diff 出差异、restore 成功还原并自动留 backup）。一个工具的最小可信度证据是"演示路径上每一步都真的发生了"，而不是"比别人快多少"。但要记住这只是可行性，不是有效性。
