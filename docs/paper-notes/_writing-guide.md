# 文献精读页写作规范

本目录产出 **9 篇论文的精读 HTML**，每篇一个独立文件，可离线双击打开。
目标是：**让一个没读过原文的人，读完这一页就能说清这篇论文做了什么、为什么这么做、结果如何、跟自己（本课题）有什么关系。**

---

## 一、硬性约束

1. **一切以原文为准。** 每个事实、数字、结论都要能在原文里找到依据，并标注页码。
   - 页码使用 `.work/papers/paged/<slug>.paged.txt` 里的 `===== [PAGE N] =====` 标记，即 **PDF 物理页码**。
   - 引用格式：正文里写「（原文 p.12）」，金句区用 `<span class="src">— 原文 p.12</span>`。
   - **禁止编造任何数字。** 拿不准就写「原文未给出」，或干脆不写。宁可少一个数，不可错一个数。
   - 禁止把二手印象（博客、他人综述）当成原文结论。只写原文写了的。
2. **不改 `<style>` 块。** 模板里的共享 CSS 必须逐字节保留（校验脚本会比对）。页面专属样式写进 `<style>` 之后另起一个 `<style data-page>`。
3. **单文件、可离线。** 不允许任何外部资源：不能引用 CDN、外部图片、外部字体、外部 JS。图一律用**内联 SVG**手绘。链接只允许指向同目录的 `index.html` 和兄弟页面。
4. **删干净占位符。** 交付文件里不允许残留 `{{…}}`、`此处放`、组件示例注释块。
5. **固定结构。** 十个 `<section id="s1">…<section id="s10">` 一个不能少，标题层级照模板。可以在节内自由加 `<h3>`/`<h4>`。

---

## 二、内容要求

| 项 | 要求 |
| --- | --- |
| 正文长度 | **2000–3500 汉字**（不含代码、表格、SVG 文本）。低于 2000 说明没讲透，高于 3500 说明在堆砌。 |
| 语气 | 简体中文书面语，**像一位耐心的师兄在白板前讲**。可以用"你"、可以用类比、可以说"这里容易搞错"。不许写成摘要翻译。 |
| 术语 | 首次出现给中文（English），之后可用英文缩写。全文术语与 `AGENTS.md` 第 3.2 节保持一致。 |
| 图表 | 至少 **1 张自绘 SVG 示意图**（讲清机制），**1 张数据表**（真实数字）。图题在下，表题在上。 |
| 批判 | 第 06 节必须写出**你自己的判断**，不能只复述作者承认的局限。 |

> **字数例外（C 簇）**：`07 noWorkflow`、`08 MSR 综述`、`09 中断恢复` 三篇上限放宽到 **7500 汉字**。
> 理由：这三篇分别对应本课题的「溯源断裂」「信息分散」「上下文丢失」，是开题报告与论文引言的
> 直接证据来源，需要更充分的原文证据、方法论细节与效度讨论；`09` 尤其要把实证数字（会话数、
> edit lag 分布、Table 15/16）讲清楚，压缩会损失可引用性。A/B 簇仍按 2000–3500 执行，
> 保持「机制与平台类论文用一张图讲透」的轻量定位。

### 各节写作要点

- **01 导读**：30 秒读懂 = 痛点 + 办法 + 结论，三句话讲完。"坐标系"段落讲清它在学术脉络中的位置（它回应谁、被谁超越）。
- **02 问题**：用具体场景讲困境，别用抽象名词。`.vs` 对比块讲"之前 vs 这篇"。
- **03 核心思想**：一句话 + 一张图 + 一段"为什么这样设计就 work"。这是全页最重要的一节。
- **04 方法拆解**：按原文真实结构拆 2–4 个部件，每个说清「输入 → 做什么 → 输出」。
- **05 实验**：先交代设置（数据集/基线/指标），再给数，再解释。要区分**实质提升**与**噪声**，并说明作者的归因。
- **06 局限**：分三层写——作者自述 / 外部质疑（如同行后续工作的批评）/ 我的判断。
- **07 与本课题**：**这是最容易被写空的一节。** 必须具体到：
  - 开题报告哪一节可以引它（对照 `thesis/proposal.md` 的章节）；
  - 系统哪个模块可以参考它的设计（对照 `AGENTS.md` 3.3 的五块研究内容）；
  - 它**不能**支撑什么（避免过度引用）。
- **08 金句**：2–4 句真正有信息量的原话，英文原文 + 中文翻译 + 页码。
- **09 术语表**：5–10 条，用本课题语境解释。
- **10 追问**：3–5 个问题，答案写在 `<details>` 里。问题要能引导重读，不是"这篇讲了什么"。

## 三、本课题背景（写第 07 节必读）

课题：**面向代码智能体的开发任务上下文追踪与代码变更溯源系统**。
核心问题四条：信息分散 / 缺少任务视角 / 溯源断裂 / 上下文丢失。
三个关键概念：开发任务（Task）、任务上下文（Task Context）、变更溯源（Change Provenance）。
五块研究内容：①信息模型与统一事件表示 ②上下文采集与关联 ③变更溯源与证据链 ④交互界面与任务续接 ⑤LLM 辅助与评估。

详细定义见 `AGENTS.md` 第 2–3 节。写第 07 节前请先读。

## 六、论文阶段引用注意（精读时发现的问题，写正文前必看）

以下几条是逐页核对原文时发现的**易误引点**，写开题报告/论文正文时直接按这里走，不要凭印象：

1. **Resumption（09）的百分比必须带"上界"**。作者在 p.26 的效度讨论中自述：edit lag 无法区分"恢复旧任务"与"思考新任务"，且观察到某活动不等于它因果地用于恢复。因此「仅 10% 的会话能在 1 分钟内恢复编辑」「83% 的会话在首次编辑前需要导航」这两个数应表述为**上界**。这两个数来自三个数据集的一致模式，是最稳的可引数据。
2. **noWorkflow（07）不能挂"低开销"的说法**。它是 4 页 PVLDB demo 短文，**原文未给出任何采集开销/性能数字**。任何"轻量""低开销""几乎无影响"的表述都不能引这篇。
3. **Resumption（09）不是实验室研究**。它是 86 名职业开发者的真实 IDE 交互日志（约 1 万会话、4,511,524 条事件）+ 414 人问卷，没有受控实验。不要写成"实验室观察研究""小样本"。
4. **MSR 综述（08）不是二维分类**。原文是**四个调查维度**（信息源 / 目的 / 方法 / 评估）+ **四层分类法**（演化对象 → 目的 → 表示 → 信息源），不要简化为"数据源 × 分析技术 × 应用"。
5. **SWE-bench（01）的 oracle 检索结果 4.8% 不是上界**，作者自己否认为上界（p.5）；「能生成可 apply 的补丁」43.07% 与「能解决」1.97% 是两个不同指标，不可混用。
6. **OpenHands（03）表 1 的"全勾"框架对比是按功能清单自评，不是实验**（p.6）；HumanEvalFix 79.3%（0-shot）与 SWE-agent 的 87.7%（1-shot）不可直接比较。
7. **SWE-agent（02）的"迭代式搜索"低于"完全不搜索"**（12.0 vs 15.7，Lite，p.6）是反直觉但有据的结论，引用时务必带上数据集与设置，否则会被当成笔误。
