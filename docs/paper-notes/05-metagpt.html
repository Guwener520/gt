把软件公司的 SOP 塞进多智能体：用结构化文档代替闲聊

MetaGPT: Meta Programming for A Multi-Agent Collaborative Framework

Sirui Hong, Mingchen Zhuge et al. · ICLR 2024 · 原文 29 页

框架 + 基准 多智能体协作 与本课题关联 ★★★★☆ 精读用时 ≈ 20 分钟
一句话结论：让五个角色按人类软件公司的标准作业流程（SOP）交接结构化文档而不是自由聊天——PRD、系统设计、任务清单、代码、测试——把「级联幻觉」挡在文档格式这道关口上。7 个开发任务上可执行性均分 3.75（满分 4）、人工返工 0.83 次，同期 ChatDev 是 2.25 与 2.5（p.8）。

01导读：三分钟建立坐标系

30 秒读懂

2023 年多智能体很热，主流做法是给几个 agent 分配角色、自由对话（CAMEL、ChatDev、AgentVerse）。本文的判断是：自由对话会把错误一路传下去，因为每轮输出都没有约束。替代方案是把软件公司的 SOP 编码进 prompt 序列——每个角色产出固定格式的文档，下游只读文档（p.1、p.6）。

坐标系要从它和 ChatDev 的关系看。两篇几乎同期（本文 2023 年 8 月，ChatDev 7 月），都在做「多角色协作写软件」但路线相反：ChatDev 用对话链，MetaGPT 用文档流水线。它们互相评价过对方——本文说 ChatDev 靠对话会丢信息（p.6），ChatDev 说本文的角色「只是遵守人类专家预定义的静态指令」（ChatDev 原文 p.5）。这对互评是理解「协作介质」最好的入口。

阅读建议

先读 §3.1（角色与流程）和附录 B（第 17–20 页）：附录里有一份完整的 PRD 与系统设计，比任何文字描述都直观。§4.4 的消融表（第 9 页）信息量最大：角色一个个加上去，返工从 10 降到 2.5。

02它要解决什么问题

你给两个 agent 分配「产品经理」和「架构师」，让它们聊需求。头两轮很像样，第五轮开始互相客套，论文里就举了两个 agent 聊午饭的例子（p.2）。更麻烦的是错误会级联：产品经理漏一个需求，架构师照着漏的需求设计，工程师照着错的设计写代码，最后没人能指出哪一步错了（p.1）。

作者把这个现象叫「天真串联 LLM 导致的级联幻觉」（cascading hallucinations）。问题不在单个 agent 不够强，而在交接物没有约束：交接自由文本时，接收方无法判断它是否完整自洽，误差就自由累积。

之前的做法（自由对话）

  • 交接物是聊天记录，格式随意、长度失控
  • 没有校验点，错误到最后一轮才暴露

这篇的做法（SOP + 文档）

  • 交接物是固定 schema 的文档（PRD、设计、任务清单）
  • 代码要真的跑，报错回灌，最多重试 3 次（p.6）
打个比方

自由对话像传话游戏：每传一手都会失真，传到第十个人已面目全非。SOP 像接力赛：交接的是接力棒本身（那份格式固定的文档），不是「我对上一棒的理解」。

03核心思想：一句话与一张图

一句话：把人类软件公司的标准作业流程编码成「角色 + 固定格式的中间产物 + 可执行反馈」三件套，让每一步的输出先满足格式，再谈内容（p.1、p.5）。

关键机制

中间产物是「可校验的契约」。PRD 里有带优先级的需求池（P0/P1 分级）（p.18），系统设计里有文件清单（p.19），任务清单把每个文件映射到一句功能描述（p.20）。下游的输入被上游的格式钉死，漏一条需求就会露出来。

文档取代对话，切断了「闲聊」这条幻觉通道。作者写得很直白：agent 之间通过 documents and diagrams 通信，而不是 dialogue，因为文档「包含全部必要信息，能防止无关或缺失的内容」（p.6）。

结构化还带来可检查性。每个中间产物人都能读、能改；工程师写完代码要真的执行，错误信息回灌，最多重试 3 次（p.6）。这让 SOP 不只是「写得更整齐」，而有了客观的通过判据。

发布订阅把通信拓扑从 O(n²) 降到 O(n)。全局消息池 + 按角色订阅，agent 只接收自己关心的前置产物（p.6）。角色越多，这个设计越必要。

因果链总结：级联幻觉的根源是「每一步输出都没有约束，误差自由累积」。SOP 给每一步加了格式约束与可执行验证两个纠错点，误差在每一步被压小——这才是它 work 的原因，不是「多了几个角色」。

04方法拆解：它到底怎么做的

  1. 角色定义五个角色：产品经理、架构师、项目经理、工程师、QA 工程师。每个角色有 profile / goal / constraints 与各自的可用工具——产品经理能搜索，工程师能执行代码（p.5）。角色不是人格设定，是职责与产出格式的绑定。
  2. 结构化交接PRD 含产品目标、用户故事、竞品分析、需求池、待澄清项（p.17–18）；系统设计含实现方案、文件清单、待澄清项（p.19）；任务清单含依赖包、API 规格、逐文件逻辑说明（p.20）。
  3. 通信协议共享消息池 + 订阅：agent 把产物发布到池里，其他 agent 按自己的订阅规则取用；收到全部前置依赖才被激活（p.6）。
  4. 可执行反馈工程师写单元测试并执行，拿到结果；不通过就调试，最多 3 次（p.6）。这是全流程里唯一的「客观判据」。

一个值得单独看的字段：待澄清项

PRD 和系统设计里都有一项「Anything UNCLEAR」（p.18、p.19）。作者没展开讲，但它是这套设计的逃生阀：允许角色显式声明「我不确定」，而不是硬编一个答案往下传。这和 ChatDev 的「沟通式去幻觉」是同一问题的两种解法——一个写进文档模板，一个变成对话动作。

容易误读

MetaGPT 不是「多智能体辩论」：角色之间不互相质疑、不投票、不协商，流程顺序写死；所谓「协作」是单向流水线 + 消息广播。把它当成「一群 agent 开会」会完全读错。

05实验与结果：数字说明什么

三个数据集：HumanEval（164 题）、MBPP（427 题）两个公开代码生成基准，加自建的 SoftwareDev（70 个任务，主实验随机取 7 个）（p.7）。指标含可执行性（1–4 分人评）、成本（时间 / token）、代码统计、生产率（每行代码的 token 数）、人工返工次数（p.7）。

怎么读？最硬的两个数是可执行性 2.25→3.75 与返工 2.5→0.83，它们直接对应「少犯错、少返工」。但要注意三点：一是 token 反而更多（31,255 vs 19,292），「更省」指的是每行代码的 token（124.3 vs 248.9），不是总成本；二是 SoftwareDev 只有 7 题、人评 1–4 分，没有评分者一致性报告；三是 85.9% / 87.7% 是「MetaGPT + GPT-4」的成绩，附录里 GPT-4 单独也有 72.4%–81.2%（p.25），幅度取决于基线怎么设。

消融表（p.9 表 3）比主表更能说明机制：只放工程师时人工返工 10 次、可执行性 1.0；加产品经理后 6.5 次 / 2.0；再加架构师 4.0 次 / 2.5；四个角色齐了是 2.5 次 / 4.0。有意思的是「产品经理 + 项目经理但跳过架构师」这一行：3 个 agent、205 行、返工 3.5 次、可执行性只有 2.0——角色数量不等于效果，缺了架构师这一环，多一个 agent 反而更差。可见 SOP 的价值在「链条完整」，不在「人头够多」。

06局限与可质疑之处

  • 作者自述：覆盖不了 UI / 前端与多模态；代码虽更多，仍难满足真实复杂需求；用户很难中途打断，也无法给每个 agent 单独设检查点（p.25）。
  • 外部质疑：ChatDev 那篇的批评是——本文的角色「只是遵守人类专家预定义的静态指令」，流程无法随任务自适应（ChatDev 原文 p.5）。这条批评成立：SOP 写死之后，任务必须「长得像软件开发」才用得上。
  • 我的判断一：消融表（p.9）其实说了一件作者没强调的事——加角色的收益几乎全在返工次数与可执行性上，而代码行数、费用都变差（$0.915 → $1.385）。SOP 买到的是「少返工」，不是「多产出」。这对本课题有用：过程结构化的价值应该用返工/验证成本衡量，而不是产出量。
  • 我的判断二：论文完全没有度量「文档质量」。它假设格式对了内容就对，但需求池本身若是错的，SOP 只会让错误传得更整齐——而且因为每步都「看起来很规范」，反而更难被发现。
  • 我的判断三：「3.75 分」这个数字不可复现：人评 1–4 分、7 个任务、没有评分细则与一致性系数。它能支撑「比 ChatDev 好」这个定性结论，但不能跟别的指标换算。写综述应引「返工从 2.5 降到 0.83」，而不是 3.75。

07与本课题的关系

怎么用

这篇给本课题一个反方向的参照。开题报告 §1.2（四）提出要「以任务为根，统一挂接对话、变更、工具调用与测试」；MetaGPT 的「任务」是事先分解好的——每个文件一个 task（p.20），边界清清楚楚；本课题的任务事后从事件流里重建，边界要靠空闲时长、目标切换、提交动作推断（开题报告 §2.1（三）第（2）条）。这个对照可写进第 3 章任务边界判定的动机段。

第二处是 Checkpoint（检查点）。本文每个角色交接时天然形成一个「过程落点」：产物完整、可读、可回退。本课题可以借这个思路，把「一次完整的交接」定义为检查点。

可借鉴

共享消息池 + 订阅 = 任务上下文视图的信息过滤机制。开题报告 §2.1（三）第（5）条的任务时间线可按「关注点」过滤，而非全量平铺。

可对照

它的「结构化中间产物」对应本课题的「变更卡片」：都是把过程压缩成可读、可校验的中间表示。区别是它由 agent 主动产出，本课题要从事件里重建。

要避开

不能引它支撑「多智能体调度」。开题报告 §2.1（四）明确把多智能体调度列为不做事项；它的角色编排是应用层逻辑，与采集/溯源层不是一回事。

再具体一点：第 2 章综述讲「智能体能力」时，这篇与 ChatDev 成对出现，说明「协作介质会影响错误传播方式」；第 4 章讲任务边界时，引它的「显式任务分解」作为理想情况，反衬隐式边界判定的难度（对应 RQ5）。但它不能支撑两件事：「事件模型」——它没有事件表示；「变更粒度」——它的产物是整份文件，没有 hunk 概念与位置映射。这两点正是分界线。

08原文金句

MetaGPT encodes Standardized Operating Procedures (SOPs) into prompt sequences for more streamlined workflows, thus allowing agents with human-like domain expertise to verify intermediate results and reduce errors.

MetaGPT 把标准作业流程编码进 prompt 序列，使流程更顺畅，从而让具备类人领域专长的 agent 能校验中间结果、减少错误。

— 原文 p.1

Unlike ChatDev, agents in MetaGPT communicate through documents and diagrams (structured outputs) rather than dialogue. These documents contain all necessary information, preventing irrelevant or missing content.

与 ChatDev 不同，MetaGPT 的 agent 通过文档与图（结构化输出）而非对话来沟通。这些文档包含全部必要信息，可防止无关或缺失的内容。

— 原文 p.6

In a company simulated by MetaGPT, all employees follow a strict and streamlined workflow, and all their handovers must comply with certain established standards. This reduces the risk of hallucinations caused by idle chatter between LLMs.

在 MetaGPT 模拟的公司里，所有员工遵守严格顺畅的流程，所有交接必须符合既定标准。这降低了 LLM 之间闲聊导致的幻觉风险。

— 原文 p.2

09术语表

标准作业流程 SOP
把一项工作拆成固定顺序、固定产出格式的步骤。本文主张「SOP 可以编码成 prompt 序列」。
级联幻觉 cascading hallucination
上游的错误没被发现，被下游当成事实继续加工，越传越偏。本课题「溯源断裂」在智能体语境下的对应现象。
结构化中间产物
有固定字段的交接物（PRD、系统设计、任务清单），既是给下游的输入，也是给人看的检查点——对本课题「变更卡片」设计直接可用。
共享消息池 / 订阅 shared message pool / subscription
所有 agent 把产物发布到一个池子，各自按规则订阅。作用是把两两通信降为广播加过滤，避免每个角色读全部历史。
可执行反馈 executable feedback
代码真的运行、报错回灌、修正后再跑，最多 3 次。它是流程里唯一的客观判据，也是「验证依据」的雏形。
pass@1
只生成一次就通过测试的比例。本课题不做代码生成评测，但读这类论文时要分清 pass@1 与 pass@k，别被「85.9%」误导。

10带着问题重读

为什么「文档」比「对话」更能抑制幻觉？仅因为格式固定吗？

不止。格式固定还带来两个效果：可穷举检查——需求池是列表，漏一条肉眼可见；可回退——文档是完整快照，出问题能定位到哪一份。对话两者都没有，只能从头重读（p.6）。

消融表里「跳过架构师」那一行为什么反而更差？

因为它有 3 个 agent、205 行代码，可执行性却只有 2.0（p.9）。没有架构师就没有文件清单与接口约定，工程师只能各自猜结构，代码量上去了但拼不起来。可见 SOP 的价值在链条完整而非角色数量——对本课题的启示是：任务上下文的完整性比信息量更重要。

它的 token 用量比 ChatDev 高 60%，为什么还说它「更省」？

因为它把「省」定义成每行代码的 token（124.3 vs 248.9，p.8），这是生产率指标而非成本指标。真实成本还要算人工返工（0.83 vs 2.5 次）；把人的时间折成钱它可能确实更省，但论文没做这个折算。
