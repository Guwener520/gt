两个角色、一条对话链：把瀑布模型拆成一场场双人对话

ChatDev: Communicative Agents for Software Development

Chen Qian, Wei Liu, Hongzhang Liu et al. · ACL 2024 · 原文 13 页

框架 + 实证 多智能体协作 与本课题关联 ★★★★☆ 精读用时 ≈ 18 分钟
一句话结论：把瀑布模型拆成 3 个阶段、5 个子任务，每个子任务只让两个角色对话——一个下指令、一个交付，并要求交付方在不确定时先反问。1,200 条需求上可执行性 0.88、综合质量 0.3953，同期 MetaGPT 是 0.4145 与 0.1523（p.6）。它用「成对对话」换掉了复杂拓扑，代价是每步只传递一份压缩过的方案。

01导读：三分钟建立坐标系

30 秒读懂

多智能体做软件，最直接的想法是让五个角色一起开会。本文反过来：任意时刻只有两个 agent 在说话，一个提要求、一个给方案，聊完就把结论交给下一对（p.4）。谁和谁聊、聊什么由写死的「对话链」（chat chain）决定（p.3）；聊的时候不确定就得先追问（p.5）。

坐标系还是它和 MetaGPT 的关系。两篇几乎同期、目标相同（多角色协作写软件），但介质相反：ChatDev 用对话，MetaGPT 用文档。本文批 MetaGPT「角色只是遵守人类专家预定义的静态指令」（p.5），MetaGPT 批本文「对话会带来无关或缺失的内容」（MetaGPT 原文 p.6）。两篇最好成对读——差异不是「谁更好」，而是信息在阶段之间怎么传递的两端。

阅读建议

正文只有 9 页，建议全读。重点三处：§3.1 的对话链形式化（第 3 页）、§4.2 的消融表（第 7 页）、第 8 页对「评审建议」与「编译错误」的统计——后者是全文最有信息量、也最容易被跳过的一节。

02它要解决什么问题

传统软件工程按瀑布模型分阶段，每阶段有专门的模型或团队。照搬到 LLM 上有两个问题：一是阶段断裂——技术选型、数据结构、接口约定前后对不上；二是一步到位不现实——让一个 agent 直接吐出整套软件，复杂任务几乎必失败（p.1、p.6）。

那让多个 agent 自由讨论行不行？作者试了，发现三种毛病（p.4）：角色翻转（该提问的开始给方案）、指令重复（要求被反复复述）、虚假回复（没解决却说「已完成」）。根因是没人管议程——没有议程，对话就会漂。

之前的做法

  • 单 agent 一步生成整套软件，复杂任务失败率高
  • 多 agent 自由讨论，出现角色翻转与虚假回复（p.4）

这篇的做法

  • 把流程写成「对话链」，每个子任务只含一对角色（p.3）
  • 用「沟通式去幻觉」强制 assistant 先追问再作答（p.5）
打个比方

自由讨论像一群人群聊改稿，谁都能插话，最后没人记得哪版算数。ChatDev 像剧组：每场戏只有两个演员对词，导演（对话链）决定这场戏是谁跟谁、演什么，演完把台词本交给下一场。

03核心思想：一句话与一张图

一句话：把「谁和谁聊、聊什么」写成一条链，把「怎么聊」约束成「先追问、再交付」，于是多智能体协作退化成五次可控的双人对话（p.1、p.4）。

关键机制

把拓扑压成链，协作才可控。形式化上，对话链 C = ⟨P₁, …, P|C|⟩，每个子任务 Pi 是一串有界对话，每条发言是角色 τ、上下文 I 与动作 A 的函数（p.3 式 1）。只有两个角色，就没人抢话——角色翻转被结构性地消掉了（p.4）。

记忆分段是省 token 的主因。长期记忆只存每个子任务的方案，短期记忆只存当前对话（p.4 式 3–5）。所以往下传的不是五段完整对话，而是五份压缩摘要——这就是它 22,949 token 比 MetaGPT 的 29,279 便宜的原因（p.6 表 3）。

去幻觉靠「先追问」。assistant 若信息不足，先向 instructor 提问、拿到补充再交付（p.5 式 6、7）。这把「我不确定」变成显式的对话动作，而不是硬编。

终止条件必须写死。子任务在「连续两次修改后代码没变」或「满 10 轮」时结束（p.6）。没有它，两个 agent 会一直客气下去——正好呼应 MetaGPT 说的「闲聊」。

因果链总结：自由对话失败的原因是「没有议程 + 没有终止条件」。对话链给议程，记忆分段给压缩，去幻觉给追问通道，终止条件给边界。四件事合起来，多智能体才从「一群人聊天」变成「一条流水线」。

04方法拆解：它到底怎么做的

  1. 对话链分解瀑布模型 → 3 阶段 → 5 子任务，每个子任务绑定一对角色：CEO→CTO、CTO→Programmer、CTO→Programmer、Reviewer→Programmer、Tester→Programmer（p.3 图 2）。子任务顺序写死，前一个不完成不进下一个。
  2. 角色实例化每个角色由一段 role prompt 定义（职位、职责、可用工具）。作者把这一步叫 agentization——把一句话的角色描述变成可执行的对话行为（p.4）。
  3. 记忆分段长期记忆存「已完成的方案」，短期记忆存「当前对话」。换子任务时，只把上一份方案塞进新的上下文（p.4）。
  4. 沟通式去幻觉assistant 若判断信息不足，先提问；instructor 补充后再交付。这一条不是可选的礼貌，而是写进 prompt 的硬约束（p.5）。

一个容易被忽略的细节：对话里用什么语言

作者统计了所有对话的用词分布：自然语言占 57.20%，编程语言占 42.80%（p.7 图 3）。这不是凑数：多智能体协作里有一半时间其实在谈「设计」（用什么结构、叫什么名字）。这也解释了「沟通式去幻觉」为何值得单独做机制——出问题的往往不是语法，是没谈清楚的需求。

容易误读

ChatDev 不是「让 agent 自由讨论出方案」。对话的内容、对象、轮数上界全被写死了；所谓「沟通」是在一个很窄的管道里进行的。把它当成「多智能体涌现协作」会读错——这篇论文的贡献恰恰是用工程约束压住了涌现。

05实验与结果：数字说明什么

自建 SRDD 数据集：1,200 条需求，5 领域 × 40 子类 × 每类 30 条（p.5）。四个指标：完整性、可执行性、一致性、综合质量；后三者由 GPT-4 打分，质量取三者乘积。基线是 GPT-Engineer 与 MetaGPT。

最扎眼的是可执行性 0.88：单 agent 只有 0.3583，MetaGPT 0.4145。跳跃太大，值得怀疑。消融表（p.7 表 4）给出解释：去掉「编码」，0.88→0.77；去掉「评审」→0.81；去掉「测试」完全不变——可执行性主要由「编码 + 评审」挣来，测试没有贡献。而作者在第 8 页承认：评审意见里 34.85% 是「功能没实现」，编译错误里 45.76% 是「找不到模块」——多智能体修的多是「漏写、漏引」这类低级问题，不是设计错误。

质量指标要小心读。综合质量是三者的乘积（p.5），ChatDev 0.3953 对 MetaGPT 0.1523，看似「2.6 倍」，其实是乘积放大了差距；单看各项，完整性 0.56 vs 0.48、一致性 0.80 vs 0.76，差距远没有乘积那么夸张。另外消融里去掉角色（\Roles）掉得最狠：可执行性 0.88→0.58、质量 0.3953→0.2212，比去掉去幻觉机制（\CDH，0.84 / 0.3094）掉得多——说明真正干活的是角色 prompt，机制只是锦上添花。

06局限与可质疑之处

  • 作者自述：系统是原型，只能生成小规模软件；评测依赖 GPT-4 打分，指标复杂且主观；多智能体的时间与 token 成本明显高于单 agent（p.9）。
  • 外部质疑：MetaGPT 那篇说对话式交接「会带来无关或缺失的内容」（MetaGPT 原文 p.6）。这条批评有实据：本文只传「方案」不传对话原文（p.4），信息丢失是设计选择，不是意外。
  • 我的判断一：「对话 vs 文档」是个不准确的对立。真正的差别是阶段之间传什么：ChatDev 传压缩后的方案（省 token，22,949 vs 29,279），MetaGPT 传完整文档（费 token，但返工 0.83 vs 2.5）。一个有损压缩，一个无损搬运——这才是成本/质量权衡所在。
  • 我的判断二：四个指标里三个由 GPT-4 打分，而它评的是 GPT-3.5 生成的东西——裁判与被评对象同源，偏好不可控。表 2 的成对胜率（对 MetaGPT 人类 88.00%、GPT-4 57.08%，p.6）差这么大，本身就说明自动评分与人的判断不一致。
  • 我的判断三：最有价值的是第 8 页的对话统计，而不是主表：它诚实地说出多智能体修的是「漏写、漏引」，不是「想错」。这提示多智能体收益有上限——能补执行层的疏漏，补不了需求理解的偏差。对本课题的「变更原因分析」很关键：若错误来自需求理解，过程记录里最有价值的是最初那句需求，而非后面几十轮对话。

07与本课题的关系

怎么用

这篇最直接的用处是示范了对话本身就是过程证据。开题报告 §2.1（三）第（4）条要求证据链含「触发来源 / 实施过程 / 快照 / 验证依据 / 后续演化」五项，ChatDev 的每段对话天然覆盖前两项：instructor 那句要求是触发来源，往返是实施过程。但粒度是子任务而非 hunk：一次「写代码」可能产出十几个文件，无法从某行代码反查是哪句话要求的。

第二处是边界识别。它的阶段边界显式写死（对话链顺序固定），本课题的边界隐式推断（空闲时长、目标切换、提交动作）。把本文当理想情况对照，正好说明 RQ5 的难点：真实会话里没有对话链告诉你「这一段结束了」。

可借鉴

角色对固定 = 每段对话有明确的两个参与者。解析 Claude Code 会话时，可用「谁在跟谁说话」作切段依据，比纯时间窗更稳。

可对照

它的「只传方案」对应本课题的「任务上下文压缩」：任务续接要生成进展摘要，同样面临「传多少」的取舍。

要避开

不能引它支撑「任务续接」或「中断恢复」——没有任务快照概念，重跑就从链头开始；也不能拿它的 0.3953 与本课题的评估指标比较。

落到写作：第 2 章综述讲「多智能体协作」时，本文与 MetaGPT 成对出现，说明「协作介质决定错误传播方式」；第 3 章讲证据链时，引它的对话结构说明「一次交互可同时承载触发与过程两类证据」。但它不能支撑两件事：「变更粒度」——没有 hunk 概念，产物是整份文件；「多来源接入」——只处理自己生成的对话，不涉及从真实智能体日志采集。这两点正是本课题要补的空缺。

08原文金句

ChatDev is a virtual software company with different intelligent agents taking on different roles… guided in what to communicate (via chat chain) and how to communicate (via communicative dehallucination).

ChatDev 是一个虚拟软件公司，不同智能体担任不同角色，由对话链指导「沟通什么」、由沟通式去幻觉指导「怎么沟通」。

09术语表

对话链 chat chain
把开发流程拆成有序子任务、每个子任务绑定一对角色的结构。它决定「谁和谁聊、聊什么」，不决定聊得好不好。
沟通式去幻觉 communicative dehallucination
assistant 在信息不足时先向 instructor 追问、拿到补充再交付的机制。作用是把「不确定」显式化，减少硬编。
角色实例化 agentization
把一句角色描述（如「你是 CTO」）扩展成可执行的行为约束与工具清单。
长期 / 短期记忆
长期存已完成子任务的方案，短期存当前对话。这个划分是它省 token 的主因，也是它信息丢失的主因。
SRDD
本文自建的 1,200 条软件需求数据集（5 领域 × 40 子类 × 30 条）。判分主要靠 GPT-4，读数字时要记住这一点（p.5）。
成对胜率 pairwise win rate
把两个系统对同一需求的产出并排，让人或模型选更好的一个。比绝对打分更稳，但仍有裁判偏好问题（p.6）。

10带着问题重读

既然去掉「测试」阶段指标完全不变，测试环节是不是多余的？

对「可执行性」确实多余（0.88 → 0.88，p.7 表 4）。但第 8 页说测试阶段会触发修改，而修改会改变代码结构——它影响的东西论文没测。这提示读消融表要看「哪一列没变」，往往比变了更有信息量。

「只传方案」到底丢了什么？

丢了推理过程与备选方案。下一对角色只看到「决定用 SQLite」，看不到「为什么不选 JSON 文件」，遇到边界情况就无法沿用原来的权衡（p.4 式 3–5）。MetaGPT 相反：文档里保留待澄清项与设计理由（MetaGPT 原文 p.18–19）。这正是「有损 vs 无损」的具体差别。

这篇论文对「过程记录」有什么可操作的启示？

三点。一是每段交互要有明确的参与者与议题，否则事后无法归因；二是终止条件要显式，否则无法判断一段交互何时算结束（本课题的边界判定同理）；三是压缩要有损可查——它只存方案，本课题至少要存「方案 + 触发它的那句话」，否则证据链在第一步就断了。
