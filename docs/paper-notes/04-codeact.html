别让模型填 JSON：把智能体的动作直接写成可执行代码

Executable Code Actions Elicit Better LLM Agents

Xingyao Wang et al. · ICML 2024 · 原文 25 页

方法框架 + 自建基准 动作空间 与本课题关联 ★★★★☆ 精读用时 ≈ 18 分钟
一句话结论：把智能体的每个动作从「填 JSON」换成「写一段可执行 Python」，在 82 个需要反复调用多个工具的复杂任务上成功率最高高出 20 个百分点、动作次数最多少 30%；真正起作用的是代码自带的控制流与数据流，而不是代码这个外形。

01导读：三分钟建立坐标系

30 秒读懂

智能体要和外界打交道，先得约定「动作长什么样」。2023 年的主流做法是让模型输出 JSON，如 {"tool":"search","args":[…]}。本文主张：让模型直接输出一段 Python，交给解释器执行，执行结果（含报错）再喂回去。作者在 17 个模型上做对照，结论是任务越复杂、越需要组合工具，代码动作的优势越大（p.2）。

放回时间线：ReAct 确立了「思考—行动—观察」循环，动作还是自然语言；2023 年工具学习工作把动作规范成 JSON，易解析但一次只能调一个工具；「用代码解题」的路线（PaL、ViperGPT）却是单轮的。CodeAct 卡在两者之间：保留多轮循环，把动作换成代码，上一轮结果真能被下一轮用上（p.14–15）。

阅读建议

先读 §2.1–§2.3（第 3–5 页），这是骨架；§A（第 14–15 页）讲它和之前用代码的工作差在哪；§H（第 24–25 页）是对 0 分结果的解剖，全文最诚实的一页。

02它要解决什么问题

让智能体「把三份 CSV 都下载、清空行、各画一张趋势图」。用 JSON 动作，它得调 download(url1)，等框架把返回路径拼进下一轮 prompt，再调 clean(path1)，再拼一次……三份文件就是九次动作加九次搬运，任何一次出错链就断。

作者把困难归为两条（p.1）：动作空间受限（只能落在预定义工具上）、灵活性受限（一次只能调一个工具）。工程上因此有三件麻烦事：表达「对所有元素做同一件事」要在框架层写循环；中间结果要靠 prompt 搬运；错误反馈要自己给每个工具写异常包装（p.3）。

之前的做法（JSON / 文本动作）

  • 一次一个工具，循环与条件要在框架层模拟（p.3）
  • 中间结果靠框架抄回上下文，窗口被数据挤占

这篇的做法（代码即动作）

  • 一段代码就是一个动作，循环条件写在代码里（p.2）
  • 中间结果存变量，留在解释器里（p.2）
打个比方

JSON 动作像在餐厅点菜：一次一道，还得靠服务员（框架）把菜端到下一道工序。代码动作像给厨房递菜谱：能有条件有循环，洗好的菜放案板上，做错了厨房会喊「没淀粉了」。

03核心思想：一句话与一张图

一句话：把智能体对外界的所有动作收敛成「一段可执行 Python + 它的执行结果」这一种格式，让动作描述、状态存储、错误报告三件事由同一种表示承担（p.3、p.4 图 2）。

关键机制

组合性把 N 步压成 1 步。一次动作里可以循环调同一工具 N 次、按条件走分支（p.2）。效果可测：M³ToolEval 上 gpt-4-1106-preview 用代码动作平均 5.5 轮，用文本动作 7.6 轮（p.5）。轮数少不只是「快」——每一轮都可能跑偏。

中间结果有地方放。这条最容易被忽略，也最关键。JSON 动作必须把上一步输出写进下一轮 prompt，窗口里塞满数据本身；代码动作把 df、res 放在解释器内存，只有 print 出来的才回到对话（p.2）。任务越长，差别越致命。

错误反馈是免费的。Python 的异常机制本来就把「哪里错、错在哪个类型」组织成可读文本，这段文本直接就是观察（p.3 表 1）。自我纠错于是不需要额外工程：模型看到 AttributeError，下一轮就换函数（p.6 图 3 有四轮自纠实例）。

模型本来就熟悉代码。预训练语料里代码占比高，不需要 few-shot 就能 import 对库（p.6 图 3 说没提供任何演示），这解释了开源模型为何能立刻用上。

四条合起来：代码是可执行的中间表示，同时承担动作描述、状态存储、错误报告三件事；JSON 只承担第一件，另两件要框架补，补得越多越容易出错。所以原子任务上几乎没差别，组合型任务才拉开（p.2、p.5）。

04方法拆解：它到底怎么做的

全文有四个部件：交互框架、两个对照实验、数据合成流程、微调与评测。

  1. 交互框架：agent / user / environment 三角色每轮 agent 收到 observation（用户指令或执行结果），可选先用思维链规划，再发出 action。发给环境的是 <execute>…</execute> 包裹的 Python，回执是返回值、stdout 或异常（p.3）。
  2. 对照实验一：API-Bank 原子调用只要求生成一次工具调用，分别用 Python 调用、JSON、固定格式文本三种写法，故意把控制流优势消融掉，只测「模型对哪种格式更熟」（p.4）。
  3. 对照实验二：M³ToolEval自建 82 题，覆盖网页浏览、金融、行程、科学、信息处理五域，每题配一套手工工具；判分为精确匹配，上限 10 轮（p.4）。
  4. 数据合成与微调用 HotpotQA、MATH、APPS 等五个数据集生成四类轨迹，再启发式筛选，得 7,139 条、约 1,058 万 token 的 CodeActInstruct（p.7 表 4）；微调时混入 69,230 条通用对话防退化（p.7）。

筛选规则比数据规模更讲究

数据筛选最能说明作者理解问题（p.18）。只保留三类轨迹：确实用了代码动作的；「先出错、后改对」的；轮数为偶数（奇数说明没按指令回话）。同时删掉一类看似「成功」的样本——全程报错、最后却答对了，因为不能让模型学会「一直执行错代码也能蒙对」。这把自我纠错从技巧变成可训练的技能。

容易误读

CodeAct 不是「让模型写代码解题」。PaL、ViperGPT 也写代码，但都是单轮的：写完跑一次，不对就判失败（p.14）。CodeAct 的关键在「多轮」——执行结果回到上下文，下一段代码据此改写上一段思路。

05实验与结果：数字说明什么

两层实验：API-Bank 测「单次原子调用写得对不对」，是控制组；M³ToolEval 测「多轮复杂任务能不能做完」，是实验组。指标为成功率与平均轮数，17 个模型全跑一遍（p.1、p.4）。

读表要看两个方向。横向看，gpt-4-1106-preview 从 53.7% 到 74.4%，是 20.7 个百分点的绝对差，同时少用 2.1 轮（p.5）；claude-2 更夸张（29.3 → 54.9）。纵向看，只有 lemur-70b-chat-v1 是 JSON 反超（15.9 vs 13.4），这正是「12/17 而非 17/17」的来源——优势是统计性的，不是普适的。

再看控制组。API-Bank 单次原子调用上，代码动作与文本动作基本打平，Mistral-7B 甚至略输（2.5% vs 3.0%，p.5 表 2）。这个「没有优势」的结果最有力：它说明 20% 的提升不是格式带来的，而是控制流与数据流在复杂任务上带来的（p.2）。

微调部分要分开看。Mistral-7B 微调成 CodeActAgent 后 MINT 域内从 18.8 提到 57.4，同尺寸最强基线只有 25.6（p.8 表 5），提升是实质的。但 Llama-2-7B 变体在 M³ToolEval 上是 0.0；作者发现模型吐出训练数据里不存在的怪异片段，怀疑来自预训练语料或底座本身弱（p.24–25）——一个没解释清楚的负结果。

06局限与可质疑之处

  • 作者自述：一是幻觉——模型可能「想象」变量内容而不真的 print 出来；二是安全——代码动作直接给了模型在沙箱里自由执行代码的权限，最坏情况下可能突破沙箱（p.9）。
  • 外部质疑：同期软件工程方向的工作走的是相反的路——不是扩大动作自由度，而是收敛成少量受控命令，理由是自由代码更易跑偏、更难审计。这不是本文承认的，是我读出的张力。
  • 我的判断一：M³ToolEval 是自建 82 题，题目由作者挑选、判分用精确匹配。题目分布是否代表真实复杂任务无从检验；精确匹配会把「算对了但格式不对」判错，且惩罚对两种格式并不对称。论文没报告人工复核，20% 的外部效度偏弱。
  • 我的判断二：「up to 20%」常被引成「提升 20%」，是误读：它是最优模型上的最大绝对提升，不是平均值，分布是 12/17（p.5）。综述里用这个数必须连着「12/17」。
  • 我的判断三：安全那段只有一段话，把「沙箱」当既定前提，没讨论权限边界与文件写入范围。对要做事后审计的系统这很要命：动作既然是任意代码，工具调用记录就不能只记工具名。

07与本课题的关系

怎么用

本篇对本课题最直接的用处是定义工具调用（ToolCall）实体的字段。开题报告 §2.1（三）研究内容第（1）条要求 ToolCall 记录「谁在什么上下文里调用了什么」，本文给了现成答案：动作 = 代码原文 + 执行观察 + 退出状态。实现上 tool_calls 表至少要有 action_code（原始代码，而非解析后的工具名）、observation、exit_status；少了前者，一旦动作里含循环，事后就无法还原「这一次对几个文件动了手」。

第二处是开题报告 §2.2（四）「关键设计」里的六步归一化：智能体给的是「意图片段」（Edit 的旧串→新串），要变成可比较的 hunk。本文从反面印证了难点：动作越自由，从动作到变更的映射越难做，所以本课题把「一个 ToolCall 产生多个 hunk」定为 1:N。

可借鉴

ToolCall 记「代码原文 + 执行输出 + 退出状态」；把 stderr / traceback 当一等证据而非日志噪声——它是「验证依据」里最便宜的那一半。

可对照

它对「一轮交互」的定义（observation → 思维链 → action）可与本课题 Turn / Message / ToolCall 的划分对齐。

要避开

不能引它支撑「任务边界判定」或「中断恢复」——它没有任务概念，一次会话就是一个任务；也不能引它证明「事件流覆盖多来源」，它只跑过一种环境。

落到写作：第 2 章综述讲「智能体能力」时，这篇放在「动作空间标准化」支线上，引出「动作格式影响可审计性」；第 3 章讲信息模型时，引它说明「ToolCall 为何必须保留原始动作文本」。但它不能支撑 RQ1 的覆盖率论证——RQ1 要的是「一种真实智能体来源的全部事件类型」，而本文只跑过 Python 解释器，与 Claude Code 那种带 Git、测试的工程环境不是一回事。

09术语表

动作空间 action space
智能体可发出的动作集合。它决定本课题「工具调用」能记到什么粒度：动作是 JSON 就记工具名与参数，是代码就得记原文。
代码即动作 CodeAct
用一段可执行 Python 作为智能体的一个动作，执行结果（含异常）作为观察。与「代码生成」的区别是它多轮、可据观察改写后续动作。
控制流 / 数据流 control flow / data flow
前者指 if、for 这类决定「执行几次、走哪条路」的结构；后者指一个工具的输出作为另一个工具的输入。JSON 动作靠框架模拟，代码里是原语。
M³ToolEval
本文自建的 82 题基准，专测需多轮多工具组合的复杂任务，判分为精确匹配，上限 10 轮（p.4）。
CodeActInstruct
本文合成的多轮交互轨迹数据集，7,139 条、约 1,058 万 token，覆盖信息检索、软件包使用、外部记忆、机器人规划四类用途（p.7 表 4）。

10带着问题重读

代码动作既然更好，为什么还要专门做 API-Bank 那个「没有优势」的实验？

因为它是控制组。若代码动作在原子调用上也大幅领先，说明优势来自「模型更熟代码格式」，与多轮、组合无关，全文因果就站不住。结果恰恰是打平甚至略输（p.5 表 2），反而把结论钉得更死。

为什么 CodeActAgent 在 M³ToolEval 上是 0 分，在 MINT 上却是 57.4？

差别在「需不需要零样本使用没见过的工具集」：MINT 域内任务与训练数据重叠，M³ToolEval 是全新工具、零样本、精确匹配。作者猜测是预训练语料 artifact 或底座弱（p.24–25），但没做消融区分。

这篇的结论能直接搬到「改真实代码仓库」吗？

不能。它的任务都是「用工具算出一个答案」，副作用只发生在沙箱内；真实仓库里的动作留下持久化变更，要考虑行号漂移、多文件依赖、回滚。本课题关心的「变更溯源」在这里没有对应物——这正是 CodeAct 的边界：它解决「动作怎么表达」，不解决「动作留下的痕迹怎么组织」。
