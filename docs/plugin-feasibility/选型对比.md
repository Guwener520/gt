# 实现形态选型对比：VSCode 扩展 / Trae 插件 / DSH 插件

> 依据：三份独立取证报告（`vscode-extension.md`、`trae.md`、`dsh.md`），全部为**文档与源码取证**，未安装、未运行、未编译任何原型。
> 取证日期：2026-10-28。凡三份报告标注「未证实」者，本文件同样不作为结论。
> 对照基准：`thesis/task-book.md`（任务书）、`thesis/proposal.md` v3（开题报告）。

---

## 一、结论摘要

| 形态 | 作为「采集端」 | 作为「展示端」 | 一句话 |
| --- | --- | --- | --- |
| **VSCode 扩展** | **B（需配 hooks）** | **A（最强）** | 纯扩展 API 观测不到别人的对话；但扩展 + agent hooks 可行，且 webview 承载三视图是最成熟的路 |
| **Trae 插件** | **C（形态不存在）** | **C（自有 UI 不可扩展）** | 无插件 SDK、无开发者平台、无发布通道；「Trae 插件」实质 = VS Code 扩展 + 宿主兼容风险。唯一价值是它的 Hook |
| **DSH 插件** | **A（能力最强）** | **B+（React + 插槽齐全）** | 宿主即智能体，`tool/call`、`tool/result`、hunk 一等可得；但 RC 版本、非公开契约、hunk 不持久、单来源 |

**推荐（不是三选一）**：

1. **采集端统一走 hook 脚本**——Claude Code / Trae / VSCode 三家的 hook 已同构，一个脚本三家通吃，直接兑现开题报告「Claude Code 官方钩子 + OpenHands 事件文件」的两种来源承诺；
2. **展示端以 Web 三视图为主形态**——与开题报告 v3 零冲突、答辩最稳、工作量已在 105 人日预算内；
3. **VSCode 扩展作为可选增强壳**（+2~3 人日）——复用同一套 React 前端与同一个本地查询 API，把开题报告里「IDE 插件列为可选」落实为加分项；
4. **DSH 插件不进主线**——能力虽最强，但 7~9 周工期 + RC 契约 + 单来源，与 105 人日预算和「两种来源」承诺双重冲突；适合作为个人效率工具或第三来源。
5. **Trae 不进论文表述**——如需引入，只能写「Trae 事件采集适配器（基于官方 Hook）」，不能写「Trae 插件」。

## 二、必须先纠正的框架问题：「三选一」是伪命题

用户把「实现形态」当成一个决策，实际是**两个相互独立**的决策：

| 决策 | 问题 | 候选 | 决定因素 |
| --- | --- | --- | --- |
| **A. 采集端** | 对话、工具调用、文件变更、命令、测试、git 从哪来？ | hooks / 扩展 API / 宿主插件 / 日志导入 | 能否拿到「语义化事件」，而非「编辑器动作」 |
| **B. 展示端** | 三视图（时间线、证据侧栏、恢复视图）长在哪？ | Web / webview / 宿主面板 | UI 成本、演示可靠性、与开题一致性 |

关键事实：**三个候选形态的差异，80% 落在展示端，而不是采集端**。因为采集这件事，三家的正确答案是同一个——hook。

- VSCode 扩展 API 观测不到其他扩展（C 级），必须配 hooks；
- Trae 根本没有插件 SDK，但它的 hook 与 Claude Code 同构；
- DSH 插件能拿全事件，是因为它**就是**宿主，不是因为「插件 SDK 更强」。

所以「选哪个插件」问错了；正确的问题是「采集用 hook、界面放哪里」。

## 三、关键证据：三家 hook 已经同构

这是本次取证最有价值的发现，它把三选一问题直接消解掉了一半。

| 宿主 | Hook 事件 | 工具调用字段 | 与 Claude Code 兼容 | 状态 | 来源 |
| --- | --- | --- | --- | --- | --- |
| **Claude Code**（CLI + VSCode 扩展） | `PreToolUse` `PostToolUse` `SessionStart` `Stop` `UserPromptSubmit` `Notification` | `tool_name` `tool_input` `tool_response` | — | 稳定（开题报告已采用） | code.claude.com/docs/en/hooks |
| **Trae** | 同上六类，同名同构 | `tool_use_id` `tool_name` `llm_tool_name` `tool_input` `tool_response` | **是**：直接读 `~/.claude/settings.json`，注入 `CLAUDE_PROJECT_DIR` / `CLAUDE_ENV_FILE` | 官方文档化（v3.3.66 上线） | docs.trae.cn/ide_hook-configuration-reference |
| **VSCode**（Copilot / Claude / Codex harness） | `sessionStart` `userPromptSubmitted` `preToolUse` `postToolUse` `preCompact` `subagentStart` `subagentStop` `agentStop` `sessionEnd` | `toolName` `toolArgs`（Copilot 格式）；`tool_name` `tool_input`（`PreToolUse` 别名，蛇形） | **部分**：`chat.useClaudeHooks` 读 `.claude/settings.json` | **Preview** | code.visualstudio.com/docs/agent-customization/hooks |

含义：

- 一个 Node/PowerShell 的 hook 采集脚本，写一次即可同时服务 Claude Code（主来源）与 Trae（可选第三来源），并为 VSCode 内会话兜底；
- 开题报告 v3 第 174 行「任务由两名开发者分别用 Claude Code（官方钩子与 stream-json）与 OpenHands（事件文件离线解析）执行」**不需要改**；
- 这也解释了为什么 VSCode 扩展报告把「扩展 + hooks」评为 B 而非 C：hooks 是官方第一次给出的、面向第三方脚本的观测点。

**但要注意两点风险**：① VSCode hooks 明确标注 Preview，跨版本可能变；② Trae 官方提示「同名 Hook 事件的输入参数和输出参数可能存在差异」，适配器必须记录字段差异，不能假设完全相同。

## 四、六类事件可见性对照（本课题的命门）

| 采集对象 | VSCode 扩展（纯 API） | VSCode 扩展 + hooks | Trae（hook） | DSH 插件（Host） |
| --- | --- | --- | --- | --- |
| 对话消息 | **不能**（只能参与，不能旁观） | **部分**（用户 prompt 可得；助手消息无稳定事件，需 JSONL 兜底） | **部分**（`prompt` + `last_assistant_message`） | **能**（`user/message` `assistant/message`） |
| 工具调用及参数 | **不能** | **能**（`tool_name`/`tool_input`/`tool_response`） | **能**（同上，含标准工具枚举） | **能（完整）**（`tool/call.arguments`、`tool/result`） |
| 文件变更 hunk | 部分（编辑器事件 + git diff 自切） | **部分**（hook 无 hunk，需 git 交叉切分） | **部分**（`Edit` 是旧串→新串，需六步归一化） | **能（Host 内存）**（`workspaceChanges.diff()` 直接给 hunk）但**重启即失** |
| 终端命令 | 能（shell integration，含退出码） | **能** | **能（含输出）**（`RunCommand`） | 部分（在 `tool/call` 参数里） |
| 测试运行结果 | 部分（Test API 是「发布」侧） | **部分**（命令 + 退出码 + 文本解析） | **部分**（文本解析，无 TestCase 粒度） | **部分**（同上） |
| git 状态 | 能（`vscode.git` 扩展 API） | **能** | 部分（只能经 `RunCommand`） | 部分（内部用 git 但只暴露摘要） |

结论：**没有任何一种形态能「开箱」满足六类事件**。差异只在「哪几类需要自己补」：

- VSCode 扩展 + hooks：补「助手消息正文」与「hunk 切分」；
- Trae：补「hunk 归一化」「测试语义」「git 状态」，且**无 UI 落点**；
- DSH：补「测试语义」「git 状态」「Task 实体」，且 **hunk 必须自己落库**（`dsh-workspace-changes` 明言摘要与 diff 只活在该 Session 的 Host 进程内，重启后历史 turn 无卡片无 diff）。

这与开题报告 v3 的判断完全一致：真正的难点不是「接入」，而是**归一化与关联**（第 162 行六步归一化、第 164 行关联三段式）。

## 五、逐形态结论

### 5.1 VSCode 扩展

**评级：采集 B（需配 hooks）/ UI A**

硬事实：

- 纯扩展 API **无法**观测 Copilot Chat / Claude Code / Cline 的对话与工具调用。`vscode.chat` 是「参与」不是「旁观」；Chat Participant 已 deprecated 且「not supported in the Copilot harness」；唯一跨扩展通道是 `getExtension(id).exports`，须对方主动导出（Claude Code / ChatGPT 未声明）。
- 但 VSCode 2026 已内建 agent hooks，且 **Claude 扩展与 CLI 共享同一份会话历史**，hooks「fire the same hook events wherever it runs: sessions in the terminal, IDE extensions, the Desktop app」（code.claude.com/docs/en/vs-code）。本机 `~/.claude/projects/<项目>/<uuid>.jsonl` 已实测含 `tool_use` / `tool_result` / `sessionId` / `gitBranch`。
- UI：`createWebviewPanel`（页签）、`WebviewView`（侧栏）、custom editor 三处均可承载 React；本机 claude-code 扩展即 React 打包。三视图可落位。
- 存储：`globalStorageUri` 放 SQLite 文件；`better-sqlite3` 需按宿主 ABI 重编（本机 Code 1.130.0 / Electron 42.6.0），`sql.js`（WASM）可零 ABI 兜底。
- 分发：`vsce package` → `.vsix` → `code --install-extension`，离线安装是官方路径，无需签名、无需市场。
- 缺口：manifest **无 `contributes.hooks`**，扩展不能「声明式」自带 hook，只能写 `~/.copilot/hooks/` 或 `.claude/settings.json` 并引导用户开启 `chat.useHooks`；hooks 为 Preview。

**成本**：整形态 22 人日；**相对纯 Web 只多 2~3 人日**（hooks 桥 + vsix 平台包）。

### 5.2 Trae 插件

**评级：C（形态不存在）**

硬事实：

- Trae 官方文档全量导航**没有**「扩展开发 / 插件 SDK / 发布 / 开发者平台」任何条目；《扩展市场》只讲安装，无「发布」节。
- Trae 基于 VS Code 内核（日志记载 1.98.2 → 1.100.3 → 1.104），支持从 VS Code 市场安装或导入 `.vsix`；官方 FAQ 明文承认「依赖了新版 VS Code 中的某些接口，则可能会导致该扩展与 TRAE 不兼容」。
- 两个易混概念都不是「Trae 插件开发」：**TRAE Plugin** 是把 Trae 的 AI 装进 VS Code / JetBrains（方向相反）；**插件市场** 是「MCP Server + Skill」封装的 AI 能力组件（消费侧）。
- 自有 UI 不可扩展：未检索到 Agent 窗口/对话面板的扩展点，三视图只能落 webview 或独立窗口，**无法嵌入对话流**——而「证据侧栏与对话并列」正是本课题的交互主张。
- 必须登录联网、积分计费：答辩机无网无法现场跑智能体。
- 唯一亮点：官方 Hook 六事件 + `tool_input`/`tool_response`，且与 Claude Code 同构可复用。

**结论**：作为「插件形态」不成立。若要用 Trae，正确表述是「Trae 事件采集适配器（基于官方 Hook）」，界面仍走 Web；论文中不能出现「Trae 插件」字样。

### 5.3 DSH 插件

**评级：B（能力最强，契约最弱）**

硬事实：

- 两类插件、同一套 cordis 组合树：Host 插件是普通 cordis 插件（`export function apply(ctx, config)`，Node 进程内），Client UI 插件是浏览器 bundle（`window.__ModuleLoader__.load`，React 18 由宿主模块表提供）。
- manifest 即 `package.json` 的 `dsh` 字段；`engines.dsh` 只声明不校验。最小结构：`package.json` + `cordis.patch.yml` + `index.js`（带 UI 再加 `client.js` 且必须预构建成单文件）。
- 第三方实例已存在：`dsh-zotero@0.13.1` 装在 `~/.dsh/profiles/desktop/node_modules/`，走 profile 的 `dsh.profile.bundles` 挂载。
- 事件：会话是**事件溯源日志**，`KNOWN_SESSION_EVENT_TYPES` 共 60 类；`tool/call.arguments`、`tool/result` 完整；`workspaceChanges.diff()` 直接给带 3 行上下文的 hunk。Client 插件经 `session/page` / `session/follow` 也能拿全事件（工具参数与结果原样透传）。
- UI：`main` 全局面板 + `sidebarRightTabs.register()` 右侧栏 tab + `shell.bottom`，三视图可落位；但**禁止 import 宿主 UI 原语**，须复制样式、只用 `--dsw-alias-*` token。
- 存储：`node:sqlite`（宿主自己就在用，FTS5 索引）或 `ctx.storageDomain`。
- 安装：`plugin_manager` 的 `install_bundle` → profile 内 `pnpm add`；支持本地目录 `link:` / `file:`，但**离线安装要求零第三方依赖**。

**致命三点**：

1. **RC + 非公开契约**：`0.2.1-rc.3`，两三周内 rc.1→rc.4；客户端包明言「They change without notice」；指南要求「以已安装的 Harness 为准」。论文里不能把 DSH 事件名写成自己的模型。
2. **hunk 不持久**：只活在该 Session 的 Host 进程内，「先跑一遍、重启再讲」时证据侧栏是空的——必须插件自己落库，等于把最难的部分又做了一遍。
3. **单来源**：只接 DSH 满足任务书「至少一种」，但**违背开题报告「两种来源」**，且丢掉「多来源接入」创新点；DSH 相对小众，评审可能质疑「换一个智能体就失效」。

**成本**：7~9 周（含学习成本），远超预算。

## 七、推荐方案

### 7.1 目标架构（与开题报告 v3 兼容）

```
采集端（与形态无关）                      展示端（可替换壳）
┌─────────────────────────────┐          ┌──────────────────────────┐
│ ① hook 采集脚本（Node）       │          │ Web 三视图（React+Vite）  │  ← 主形态，答辩主界面
│    Claude Code / Trae / VSCode│  →SQLite→ │  VSCode 扩展 webview      │  ← 可选增强（复用同一前端）
│ ② Claude JSONL 导入兜底       │          │  （同一份查询 API）        │
│ ③ OpenHands 事件文件解析      │          └──────────────────────────┘
│ ④ git 交叉校验 + 测试结果解析  │                      ↑
└─────────────────────────────┘                 查询 API（本地 HTTP）
                     ↓                                  │
              统一事件模型（八实体）+ 关联/溯源引擎 ───────┘
```

要点：

- **hook 脚本是唯一采集入口**，输出直接落 SQLite，与开题报告「单机 SQLite」一致；
- **前端只依赖查询 API**，因此 Web 与 VSCode webview 可以共用同一套 React 代码——这是把「可选 IDE 插件」压到 +2~3 人日的关键；
- **DSH 插件若做**，定位为「第三来源适配器」或「个人效率工具」，不进主线。

### 7.2 工期影响

| 方案 | 增量 | 相对开题 105 人日 |
| --- | --- | --- |
| Web + hook（基线） | 0 | 0（预算内） |
| + VSCode 扩展壳 | +2~3 人日 | 需从机动时间挤，或砍一个次要视图 |
| 改 VSCode 为唯一形态 | +22 人日 | 不可行（预算已超 90 小时） |
| 改 DSH 为唯一形态 | +35~45 人日 | 不可行 |
| 加 Trae 采集适配器 | +0.5 人日 | 可接受（复用 Claude hook 管线） |

### 7.3 如果坚持单选，按目标选

| 你的真实目标 | 选 | 理由 |
| --- | --- | --- |
| 答辩最稳、最快出活、不改稿 | **Web** | 与开题 v3 零冲突，105 人日预算内 |
| 想做成「真能日常用」的工具 | **VSCode 扩展**（+hooks） | 你本机已装 Claude Code 扩展，日常就在 VSCode 里干活 |
| 想做「最前沿、能力最强」的 demo | **DSH 插件** | 宿主内事件最全，但工期与契约风险要自己扛 |
| 想用 Trae | **不要选它做形态** | 只把它当 hook 来源，界面仍走 Web |

## 八、对开题报告的影响

**若按推荐方案（Web 主 + VSCode 可选壳）**：

- 开题报告 v3 **无需修改**。第 99 行「界面限定为 Web 形态的三个核心视图，IDE 插件列为可选」正好被落实；
- 第 174 行采集来源「Claude Code 官方钩子 + OpenHands 事件文件」不变，可选加 Trae 作为第三来源（+0.5 人日）；
- 第 236 行工作量表「不做 IDE 插件 −5 人日」保持；若最终做扩展壳，需在论文第 5/6 章说明「复用同一前端与 API，增量 2~3 人日」，不推翻预算。

**若改为主形态为插件**（不推荐），需动：四(四) 研究边界、六(二)(三) 技术路线与架构（**图 6-2 必须重绘**）、表 7-1 载体、九 创新点，约 900~2500 字 + 1 图；VSCode 约 1~1.5 人日，DSH 约半天到一天但牵动「两种来源」一致性。

## 九、待验证与风险

1. **VSCode hooks 为 Preview**：答辩前须锁定 VSCode 版本，并在论文中注明「基于 1.130.0 的 Preview 特性」；若答辩机版本不同，改用 Claude Code hooks 主路径（稳定）。
2. **Trae 会话库位置未公开**：只能靠 hook 落盘，不能直读会话；且必须登录联网，现场演示只能回放 fixtures。
3. **DSH 未证实项**：交互式终端命令是否落事件、第三方插件调 `node:sqlite` 是否被鼓励、`dshmarket` 的离线策略。
4. **三家 hook 字段差异**：Trae 官方已提示同名事件参数可能不同，适配器必须按来源记录版本与字段映射，不能假设同构即同字段。
5. **本报告未做运行时验证**：所有「能否跑通」的判断均来自文档与源码，落地前需按 `docs/开题报告-v3修订说明.md` 的 Spike 1 实测。
