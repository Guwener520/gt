## 一、总评

v5 在事实、结构、数字上没有问题，语言毛病集中在三类：**一是压缩过度造成的电报式与口语化表达**——「这带来三个问题」「需人工翻找」「在典型编程任务上实验」这类句子缺主语、缺中心词，读者要回头补出谁做什么；**二是并列与层次失控**——二部分两段以分号串起多组动宾（第 1 段两组、第 2 段三组），分句之间主语来回跳换（「实现任务中心……，任务中断后生成进展快照并支持跳转到证据」），必须回读才能确定动作的发出者；**三是术语与体例不统一**——工具执行/工具调用、事件来源/事件源、基线方式/基线、任务/开发任务、测试/测试运行，以及「第9周」与「表 4-1」「共 32 周」的空格体例相冲突。规范性语气（「本课题要求学生完成以下工作」）与客观性基本合格，没有夸张词与主观评价；规范上的硬缺口是三处课题术语未按 §5.1 给英文，以及一处括号内用顿号连接小句。

## 五、完整润色建议稿（一、二、三、四、六节）

> 说明：以下为可直接比对取用的定稿建议。第五部分 18 条文献、表 4-1、封面信息一律不动；落笔时须同时改 `thesis/task-book.md` 与 `latex/chapters/taskbook_body.tex`（AGENTS §7）。

### 一、课题背景

代码智能体（code agent）已逐渐应用于日常开发：开发者以自然语言描述任务，由智能体完成代码分析、文件修改、工具调用、测试执行与问题排查。但对话、代码差异、工具调用与测试结果分散在不同界面，缺少围绕开发任务（task）的组织与关联。由此产生三方面问题：（1）缺乏任务视角：多轮修改与中断重启时难以掌握当前进展；（2）修改原因不可回溯：代码为何被改、依据哪次测试验证，需依靠人工查找与回忆；（3）中断后上下文丢失：重新开始需重读长对话与大量差异。

本课题面向单个开发者，研究开发任务、对话、代码变更、工具调用与测试结果之间的关联与组织方法，设计并实现支持任务上下文（task context）追踪与代码变更溯源（change provenance）的原型系统，帮助开发者围绕任务查看证据链，并在中断后恢复上下文。

### 二、应完成的主要内容

本课题要求建立开发任务、对话、工具调用、文件变更、测试运行等实体的信息模型，设计统一的事件表示、可扩展的事件模式与存储结构；同时接入至少一种真实代码智能体的事件源，结合 Git 与测试输出采集开发过程数据，研究将异构记录关联到任务的方法。

在此基础上，以变更块为粒度生成“变更卡片”，记录触发来源、实施过程、修改前后快照与验证依据，支持“代码—原因—证据”的双向查询；实现任务中心、任务时间线与变更证据侧栏三个视图，并在任务中断后生成进展快照，支持由快照跳转到相应证据；同时探索利用大语言模型生成任务摘要、整理开发进展（其输出须绑定原始证据，证据不足时弃答），并在典型编程任务上与基线方法对比评估。

### 三、基本要求及应完成的成果形式

本课题要求学生完成以下工作：

1. 调研代码智能体、开发过程追踪与变更溯源的研究与产品现状；
2. 设计开发任务、对话、工具调用、文件变更、测试运行等实体的信息模型；
3. 实现任务上下文追踪与变更溯源原型系统，接入真实代码智能体事件源；
4. 在典型编程任务上开展实验，与基线方法对比，形成可复现的实验数据；
5. 撰写毕业设计论文，说明需求、设计、实现与评估过程。

成果形式：可运行的原型系统一套（含源码、部署与使用说明）；毕业设计（论文）一份；系统设计、测试与评估报告，以及实验数据；演示视频与答辩幻灯片。
