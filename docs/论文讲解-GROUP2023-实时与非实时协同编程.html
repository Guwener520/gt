把“边写边同步”的实时协同，接回“提交—diff—blame”的 Git 世界

Yifan Ma, Batu Qi, Wenhua Xu, Mingjie Wang, Bowen Du, Hongfei Fan（同济大学软件学院 / 华威大学）

核心思路

一分钟版本

实时协同编程（多人同时编辑同一份代码、改动即时同步）很高效，但它和 Git 这套“非实时协同”是割裂的：会话结束后由一个人提交，Git 只看到“提交者”，看不到“每一行到底是谁改的”。git blame 因此失真，代码评审、绩效统计、新人接手模块都会受影响。

论文做了三件事：① 提出一套可在两种协同方式间来回切换的工作流；② 设计 Colored Lines Algorithm，把会话期间的编辑操作历史映射到 Git diff 的每个变更块上，从而按作者拆成多个 commit（一作者一提交）；③ 实现两个 IDE 插件并做用户评估与性能实验。

一句话：它解决的不是“怎么同步”，而是“同步完了以后，历史记录还认不认得出人”。

01 / BACKGROUND

两种协同范式，各有各的“历史观”

理解这篇论文，先要接受一个前提：软件开发的协同有两条技术路线，它们对“变更”的记录方式根本不同。

表 1 · 非实时协同与实时协同的对照（据论文第 2 节整理）
维度非实时协同（VCS / Git）实时协同（RCP）
同步时机本地改动私有，手动 commit / push 才共享编辑操作即时传播并应用到他端
耦合程度松耦合、长周期紧耦合、短会话
冲突处理Git 检测冲突，人来解决底层一致性算法（OT）自动合并
历史单位commit + diff（按行）编辑操作（按字符/区间）
归属信息author / committer 字段，可 blame不记录——这正是论文要补的洞
关键观察

两种范式的“原子”不一样：Git 的历史原子是 commit 里的 diff 块，实时协同的历史原子是 编辑操作。论文的全部技术难点，就来自这两个坐标系对不上——这也是它最有借鉴价值的地方。

02 / PROBLEM

问题：会话一结束，作者就“蒸发”了

论文用了一个非常清楚的例子（第 2 节末）：Alice 和 Bob 在同一个实时会话里，Alice 改 funcA、Bob 改 funcB。Bob 先走，Alice 收尾提交。由于实时协同把所有改动都应用在 Alice 的工作副本上，Git 视角下这些改动全部是 Alice 的贡献。

后果链条

blame 失真 → 代码评审找不到该找的人 → 新人不知道某模块的“owner” → 用 git 记录做绩效/工单分派的自动化工具直接算错。论文的受访者 P3、P11 都提到了这类真实用法。

那为什么不学 Google Docs 那样标记“谁改的”？论文专门解释了三个差异（第 2 节）：

  • 对象不同：编程要处理整棵源码树，创建/删除/重命名文件目录很频繁，文档协同几乎没有；
  • 锚点不同：文档协同按“编辑操作”即时标记；Git 的归属建立在 commit + diff 算法 上，而 commit 是人事后手动触发的；
  • 时机不同：操作发生时还不知道它最终会落在 diff 的哪一块——中间可能被别人的插入/删除挤走，甚至被整体删掉。

最后一条是真正的难点，也是后面算法的用武之地。

03 / MOTIVATION

先做用户研究，再定设计目标

论文没有直接开做系统，而是先跑了一轮探索性研究（第 3.1 节）：85 份有效问卷（剔除无 Git 经验者）+ 30 人半结构化访谈，受访者覆盖企业工程师、教师与学生。

85份有效问卷
30人接受访谈
91%认为“追溯贡献者”对排障很关键
58.8%经常用 Git 查看分支/提交、判断代码作者
7 人主动提出“两种协同方式来回切换”的困扰

由此提炼出三条设计目标（第 3.2 节），后文每个技术选择都能对上号：

目标 A · 切换要顺

实时与非实时之间能流畅往返，会话结束后提交要自然；同一项目里不同人可以各用各的方式。

目标 B · 与 Git 无缝

必须兼容程序员熟悉的 Git 分支模型与 diff 算法（如 Myers），归属过程自动、透明。

目标 C · 支持高级实时协同

跨 IDE、可并发增删文件、冲突自动消解且保证一致性（直接复用成熟的 OT）。

写作上值得学的一点

“58.8% 的人依赖 blame”这句话不是装饰：它把“技术缺陷”翻译成了“用户需求”，后面的系统设计因此有了合法性。你的开题报告里“开发者需要恢复上下文”这类论断，也应有类似的量化或访谈支撑。

04 / WORKFLOW

工作流：创建 → 加入 → 协作 → 提交

4.1 创建与加入会话

任何人基于一个 Git 仓库就能发起实时会话：工具把本地文件推到协同服务器，服务器充当操作传播与同步的中心。其他人加入时，先被要求把未提交的本地改动 commit 掉，然后按本地状态分三种情况处理：

表 2 · 加入会话时的三种环境（论文 4.1 节）
本地状态系统动作
从未 clone 过仓库从协同服务器自动 clone，并切到创建者所在分支
已 clone，且与创建者同一 commit无需同步，直接开始协作
已 clone，但不在同一 commit自动 fetch，并 reset 到会话当前所在的 commit

同步完成后，新成员会补收“从会话创建到此刻”累积的所有编辑操作，于是所有人的代码副本完全一致。不在会话里的同事照常走非实时流程，等会话成员切回去再 push / merge。

注意这个设计

“加入 = 对齐到某个 commit + 回放操作历史”，本质上是一次状态快照 + 增量重放。这正是你课题里“任务中断后恢复上下文”可以借用的机制原型：恢复不是恢复聊天记录，而是恢复到一个可继续工作的确定状态。

4.2 会话中的两类编辑操作

会话期间可以并发做两类操作：文件内容级（在文件里插入/删除字符串）与文件树级（创建、删除、重命名文件与目录）。并发导致的操作冲突（经典的“两人同时在同一位置插入，两端顺序相反”）交给底层 OT 保证收敛，论文明确说这是“采用成熟方案”，不是本文贡献。

4.3 离开与提交：三种模式

这是全文的枢纽。会话结束时由某个人代为提交，但“怎么记”有三种选择（论文 4.3 节，图 3）：

Mode A

Single Commit

所有改动打成一个 commit，author 与 committer 都是执行提交的人。

最简单，适合结对编程、协同调试

完全丢失会话内的归属，等于没解决本文问题

论文把它当作对照基线

Mode B

Detailed Single Commit

仍是一个 commit，但在 message 里写入所有协作者姓名/邮箱，标记为共同作者（co-authors）。

成本极低，GitHub 等平台原生支持多作者

blame 仍归到提交者，行级归属依旧缺失

Mode C

One Collaborator One Commit

按 diff 块分析出每块的真实作者，迭代暂存，生成一串 commit：一作者一提交。

blame 精确到行，作者即真实作者

实现复杂，需要“操作历史 ↔ diff”对齐算法

论文的主贡献，也是用户最偏好的长期方案

图 1 · Mode C 的提交链：author 是真实作者，committer 是执行提交的人。后续 git blame 即可逐行看到真实归属。

06 / TECHNIQUE

核心技术：Colored Lines Algorithm

6.1 架构：三层，服务端管同步，客户端管历史

系统建在作者团队此前的 CP-ROOF 框架上（论文 5.1 节，图 4），分三层：

Collaboration Server

接收并传播编辑操作；内嵌一个 Git 服务器，支撑 4.1 的 clone / fetch / reset 同步。

Collaboration Client

通用接口与公共类；实现 OT 一致性维护；保存会话期间全部细粒度编辑历史；执行三种提交模式。

IDE Adaptor

插件层，处理用户操作与平台相关 UI（启停会话、执行提交），由此实现跨 IDE。

架构上的关键决定

“客户端保存完整编辑历史”是整套方案的前提。没有这份操作日志，事后就不可能反推归属。换句话说：归属能力是采集时决定的，不是提交时补出来的——这条对你做“变更溯源”同样成立。

6.2 难点：操作坐标 ≠ diff 坐标

提交时，Git 用 diff 算法（如 Myers）算出“哪几行被增删”。但会话期间的编辑操作是按字符位置记录的，而且会互相影响：

  • 某人在你插入的那行之前删了一行 → 你的行号要前移；
  • 某人在你插入的那行之前又插了内容 → 你的行号要后移；
  • 你插入的内容后来被别人删掉 → 这次插入的最终效果为零，不应产生 diff 块；
  • 你插入的行后来被别人改写 → 按“最后修改者”原则，这一行归他。

论文为此定义了两个推断函数（算法 2 给出 postEffect，preEffect 对称）：

postEffect(ATOM_OP, 后续操作, LinesY)

把一次原子编辑（如“在第 5 行末插入字符 A”）的位置，沿其后的所有操作推演到协作结束时的最终行号。若该内容已被删除，返回 −1（无效果）。

preEffect(ATOM_OP, 之前操作, LinesX)

反向回溯到协作开始前的坐标，用来定位“这次插入在原始文件里的位置”，从而对上 diff 中“新增行”的编号。

6.3 算法四步

  1. 取两端快照。用 Git 拿到协作前 LinesX 与协作后 LinesY，并算出 diff 块列表 CH。
  2. 给行“上色”。遍历全部编辑操作 OP，把每个原子操作拆开，分别用 preEffect 写入 colorMapX、用 postEffect 写入 colorMapY，值为该操作的发起站点（作者）。同一行被多次覆盖时，保留最后一次。
  3. 原子化 diff。把 Git 的 diff 块拆成“单行级”变更 CH'，使每块只对应一行新增或一行删除。
  4. 按作者分派。新增行查 colorMapX，删除行查 colorMapY，得到每个变更的作者；再按作者分组、迭代暂存，生成一串 commit。

6.4 一个走查例子

假设协作前文件如下，A 在 void c() {} 之后插入一行，B 随后删掉了 void b() {}：

A · insert 在第 4 行后插入 int x = 1;
B · delete 删除第 2 行 void b() {}
LinesX · 协作前
1public class Demo {
2 void a() {}
3 void b() {}B 删
4 void c() {}
5}
LinesY · 协作后
1public class Demo {
2 void a() {}
3 void c() {}
4 int x = 1;A 增
5}

如果没有 postEffect，A 的插入操作记录的是“第 5 行前”，而最终它落在第 4 行——直接按操作坐标去对 diff，就会错位。算法先把 A 的插入推演到 Y 的第 4 行，再与原子化后的 diff 块（新增第 4 行）对齐，于是这一块被正确判给 A；B 的删除则通过 postEffect 落到 Y 的相应位置，判给 B。最终生成两个 commit：一个只含 B 的删除，一个只含 A 的新增，二者之和等于 Git 原始 diff。

规则要说清楚

论文明确采用“行的最后修改者”作为归属规则：A 插入的行若之后被 B 改写，该行归 B；被整体删除的插入不产生 diff 块，也就不归属任何人。这与 git blame 的语义一致，但也意味着“共同编辑同一行”的协作过程会被压缩成一个人——这是可讨论的设计取舍，不是 bug。

07 / PROTOTYPE

两个插件：CoEclipse 与 CoIDEA

用 Java 实现（复用 CP-ROOF），分别做成 Eclipse 与 IntelliJ IDEA 插件（论文 5.3 节）。UI 上只有两处关键交互：编辑器里实时看到对方改动；一个 Git Integration 按钮，点开选提交模式、填（系统预填的）提交信息，系统自动暂存并提交。

  • 提交信息模板自动带上协作者与会话时间等信息；
  • 生成的提交可直接用 git log、GitKraken 等常规工具查看（论文图 8、图 9 展示了三作者会话生成的三条提交）；
  • 跨 IDE 是硬需求：同一会话里 Eclipse 与 IDEA 用户可以一起编辑同一个文件（论文图 6）。

09 / LIMITS

局限与可质疑之处

论文自述的未来工作（第 7 节）：支持“部分提交”（只挑一部分改动文件）、把算法扩展到文件/目录级操作、把评估从实验室推向工业场景与更长会话。

除此之外，读的时候可以自己补几条批判性判断：

维度问题严重度
归属语义“最后修改者优先”会把协作过程压平成单人贡献；对“共同编写”的场景可能失真，也未提供多作者标注中
覆盖范围算法只处理文件内容；文件/目录的创建、删除、重命名尚未纳入（作者自述）中
性能2500 次操作约 3 秒，属可感知停顿；论文未给复杂度分析，也未见增量式计算中
评估效度n=13、5 队、实验室、12 分钟任务；无对照组的量化比较，SUS 仅描述统计，无显著性检验中高
边界情形未讨论“会话成员与非会话成员并发修改同一文件”时的合并与归属（实际交给 Git，可能再次丢失归属）中
生态绑定只实现 Git；作者称可扩展其他 VCS，但未验证低
10 / RELEVANCE

与你课题的关系：可迁移的是“管线”，不是“场景”

这篇论文属于上一轮清单里我标为“强相关”的第 4 篇。它不研究代码智能体，但它和你课题共享同一个结构性难题：

共同难题

“变更发生时的记录”与“变更沉淀后的历史（diff / commit / 文件现状）”是两套坐标系，中间隔着别人的插入、删除、改写与时间。谁能把两套坐标对齐，谁就能回答“这段代码是怎么来的”。

论文对齐的是操作 ↔ diff 块（回答“谁改的”）；你要对齐的是事件（对话/工具调用）↔ 变更块 ↔ 测试（回答“为什么改、依据什么”）。方法同构，目标不同。

Mode C：一作者一提交按来源把变更块分组，生成“变更卡片”分组粒度与提交策略的设计权衡
git blame 归属查询从代码行反查请求/对话/测试（双向溯源）“从代码出发”的查询入口设计
加入会话时对齐到同一 commit + 回放操作任务中断后的上下文恢复（Checkpoint）恢复 = 快照 + 增量重放，而非重读聊天记录
三种提交模式任务快照的三种粒度（单快照 / 带摘要 / 按变更来源拆分）给用户“记录多少”的选择权，而非一刀切

10.2 可以直接借的三点

  1. “操作日志 → 原子化 diff → 归属”的三段式管线。你的“事件 → 变更块 → 证据链”几乎是同一根管线的另一种输入输出，可以在论文里明确写成方法来源，并说明你把“作者归属”扩展成了“原因 + 验证依据”。
  2. 以成熟 diff 为锚点，不自造坐标。论文坚持对齐 Myers diff，好处是结果能被 git blame、GitKraken 等既有工具直接消费。你的系统也应尽量让产物落到 Git 可读的形态（如变更块与 commit 关联），而不是只在自家数据库里成立。
  3. 评估写法。“小样本 SUS + 半结构化访谈 + 关键步骤性能实验”这套组合，与你开题报告里 4—5 人、SUS 必做、NASA-TLX 可选的设定高度一致，可直接作为写法参照与对照文献。

10.3 不能照搬的三点

  1. 一致性不是你的问题。OT/CRDT 解决多人同时编辑的收敛，而你的场景是单开发者 + 智能体，冲突主要发生在“人对智能体改动的接受/回退”，不是字符级并发。
  2. 主体是异步的。智能体的改动往往由一次工具调用批量产生（整个文件重写、多个 hunk 一起出现），粒度天然是 hunk 而非逐字符；直接套“按操作上色”会很别扭，应按“工具调用 → 文件写入 → diff 块”对齐。
  3. 论文只回答“谁改的”，你要回答“为什么改、依据什么”。这是你相对它的增量：把对话意图与测试结果接进证据链。写作时务必把这一点讲成“扩展”，而不是“重复”。

11 / Q&A

如果答辩被问到这篇论文

它和你的课题到底什么关系？

方法同源、场景不同。它解决“多人实时协同后，Git 历史认不出作者”；我解决“单开发者用智能体时，代码变更认不出来源与依据”。我借鉴的是它“操作历史 ↔ diff 块对齐”的管线与“采集时存全量历史”的前提，扩展的是把对话意图与测试结果纳入证据链。

为什么它不直接用 Git 的 co-author 标记（Mode B）？

因为 co-author 只写在 commit message 里，git blame 仍然把每一行归给提交者，行级归属没有解决。Mode B 的定位是“最低成本的留痕”，不是精确归属。

它为什么不用 CRDT，而用 OT？

一致性层不是它的贡献，它直接复用了团队成熟框架 CP-ROOF 的 OT 实现。对它而言一致性是前提条件，真正的难点在“历史 → diff 的归属”。换成 CRDT 也不影响其核心算法。

为什么一定要绕回 diff，不直接记录操作？

因为要与 Git 生态兼容：blame、log、各类 Git GUI 都基于 commit + diff。只有把操作历史映射回 diff 坐标，产物才能被现有工具链消费，用户才不用换工具。

“最后修改者优先”合理吗？

与 blame 语义一致，工程上可解释；但会掩盖共同编辑的过程，尤其结对编程时一行可能被两人反复改。可作为局限讨论，也可提出扩展：保留多作者标注或按编辑区间细分。

它的评估够不够硬？

不够硬，但与其定位匹配：13 人、5 队、实验室任务、SUS 描述统计、无显著性检验。它能支持“可用、性能可接受”的结论，不能支持“显著优于传统方式”。引用时应如实描述，不宜写成“实验证明显著提升”。
