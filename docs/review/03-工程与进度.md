## 一、总体判断

1. **按现方案，7 个月内不能交付。** 五块研究内容 + 5 个界面视图 + LLM 辅助 + 两轮实验 + 论文，按 8 小时/人日折算约需 **139（最紧裁剪）～221（现方案）人日**；而 2026.11–2027.05 名义可用工时为 600–750 h（**75–88 人日**），扣除期末周、寒假、春节后有效工时更低。缺口 1.6～2.5 倍，不是"排期紧"，是范围与资源不匹配。
2. **最大的技术风险被写成了一句断言。** 第 214 行用一句话交代全部数据可得性，既没有实测证据，也没有给出任何样例事件；而本课题的全部后续工作（关联算法、证据链、界面）都建立在这条链路上。经核实，该论断**部分成立但表述失准**：Claude Code 的 JSONL 被官方明确声明为"内部格式、随版本变化、不建议脚本直接解析"；Aider 的会话记录是 Markdown 而非 JSONL；Cursor IDE 会话没有公开导出格式。
3. **创新点 1 的对比前提已被现实削弱。** 第 83/234 行"现有工具以会话或文件为单位"忽略了 Cline 的 task 级会话目录 + shadow-git 逐次工具调用快照、Aider 默认每轮自动 commit、Cursor / Gemini CLI / Claude Code 的 checkpoint 机制。必须把差异从"有没有对齐"改口径为"对齐结果是否**持久、跨会话、可查询、带验证依据**"，否则答辩现场一句"Cursor 不是有 checkpoint 吗"即可击穿。
4. **进度表日期与甘特图数值一致，但甘特图有两处硬缺陷**（第一阶段标签被色块遮挡、"开题"里程碑线视觉上落在 2026-12-01 网格线上），且全表 11 个阶段首尾相接、**零缓冲**，与第 218 行"已在进度安排中预留缓冲"直接矛盾。
5. **合规与可复现性完全缺位。** 会话日志会包含 API key（Cline 官方文档明确把 provider 凭据存在 `~/.cline/data/settings/providers.json`）与私有代码；把代码送第三方 LLM API 无任何约束；第 269 行只承诺"复现脚本"，没有样例数据规模、没有离线可运行承诺，而答辩现场无网络时 LLM 功能如何演示没有答案。

**结论**：选题与方案方向正确，工程判断大体成立，但**当前形态不具备开题通过条件**——必须先补 3 个 spike（第二节末与第六节），并按第五节把范围砍到 P0，才谈得上"可行"。

### 结论（a）：第 214 行"主流智能体都有结构化日志（JSONL）"这一可行性论断是否成立？

**部分成立，但表述失准，不能作为方案的唯一前提。**

- 成立的部分：Claude Code（hooks / stream-json / jsonl）、Cline（SQLite + 会话目录）、OpenHands（事件目录）、Cursor CLI（NDJSON）、Gemini CLI（检查点 + `/chat share`）都能提供机器可读的事件流，**"消息→工具调用→文件变更"这条链路在 5 家中至少 4 家可直接获得**。
- 不成立/需修正的部分：
  1. **不是"都有 JSONL"**：Aider 是 Markdown + git commit；OpenHands 是"一事件一 JSON 文件"；Cline 是 SQLite + 目录；Cursor IDE 没有公开导出格式。
  2. **JSONL 不是稳定接口**：Claude Code 官方明确说该格式为内部格式、随版本变化，直接解析的脚本"可能在任意版本失效"，并推荐 hooks / `--output-format stream-json` / Agent SDK。报告把它当作稳定前提，属于**把易变实现细节当契约**。
  3. **保留期风险**：Claude Code 转录默认约 30 天清理、checkpoint 仅保留最近 100 个。若采集器只在实验结束后才去读日志，数据可能已被清理——采集必须**实时或会话结束时归档**（`SessionEnd` hook）。
  4. **凭据混入风险**：Cline 的 `providers.json` 与 `~/.claude` 配置目录与日志同源，采集器若整目录拷贝会带走 API key。

**改写建议（第 214 行替换为）**：

> 主流代码智能体均提供机器可读的过程记录，但接口形态与稳定性差异显著：Claude Code 提供全生命周期 hooks 与 `--output-format stream-json`（其本地 `.jsonl` 转录为内部格式，官方声明随版本变化，故仅作降级通道）；OpenHands 将每个事件序列化为独立 JSON 文件；Cline 以会话为单位存于本地 SQLite 并用 shadow git 逐次记录快照；Cursor CLI 提供 NDJSON 事件流；Aider 仅提供 Markdown 对话记录与 git 提交。本课题据此采用"**官方事件接口为主、日志直读为辅**"的采集策略，为每个来源实现独立适配器并记录来源版本号，同时以 `fixtures/` 固化一份已验证的样例数据，保证格式变化时可回归。

### 结论（b）：第 83 行"现有工具的组织单位是会话或文件"是否准确？

**不准确，创新点 1 的对比前提被削弱，必须改口径。**

事实是：现有工具的组织单位确实是**会话/任务**（Claude Code session、Cline task、OpenHands conversation），但它们**已经在会话内做到了"工具调用 ↔ 文件变更"的细粒度对齐**：

- Cline：shadow git，**每次工具调用后**提交一次快照，可 Compare 出该步 diff；
- Gemini CLI：`--checkpointing` 下**每个 tool call** 一个快照，`/restore <tool_call_id>` 可精确回滚；
- Claude Code：**每次开启一轮的 prompt** 一个 checkpoint，可 `/rewind` 还原代码或对话；
- Cursor：Agent 在显著修改前自动建 checkpoint，本地存储、与 Git 分离；
- Aider：`--auto-commits` 默认 True，**每轮修改自动提交**。

也就是说，"变更 ↔ 触发轮次"的**局部对齐**已经被商业工具部分实现。真正没有被满足的是另外四件事，而这四件才是本课题应当主张的差异：

1. **持久性**：checkpoint 是易失的——Claude Code 仅保留最近 100 个、快照约 30 天清理；Cursor 的 checkpoint 与会话状态绑定；Cline 的 shadow 仓库依附于项目目录。它们不是可长期审计的证据。
2. **跨会话/任务级聚合**：所有对齐都封在**单个会话内**；一个开发任务跨 3 次会话时，没有任何工具能给出统一视图（这一点第 234 行"可验证差异"其实说对了，但前提句写错了）。
3. **验证依据**：checkpoint 只记"文件变成了什么样"，不记"哪次测试运行验证了这个变更、结果如何"。
4. **可查询性**：checkpoint 是 UI 里的回滚按钮，不是可 SQL 查询、可按代码位置反查的图结构。

**改写建议（第 83 行与第 234 行替换为）**：

> 现有客户端（Claude Code、Cursor、Cline、Gemini CLI）已提供会话内的 checkpoint 机制，能在"某轮对话/某次工具调用"与"文件快照"之间建立**过程内、易失**的对应关系：Claude Code 每轮 prompt 一个 checkpoint 且仅保留最近 100 个、约 30 天后清理；Gemini CLI 每个工具调用一个快照；Cline 用 shadow git 在每次工具调用后提交。这些机制的共同局限是：**绑定单个会话、有保留期、不可跨会话查询、不记录验证依据、不暴露为可查询结构**。本课题的差异不在于"是否建立了对应关系"，而在于把对应关系**持久化为以开发任务为根的证据图**，补齐"验证依据（测试运行）"与"后续演化（回退/重写）"，并提供双向可查询接口与可交互界面。

按此改口径后，创新点 1 从"别人没做"变成"别人做了过程内的、易失的、不可查询的版本，我做成跨会话的、持久的、可查询的版本"——这个表述**经得起答辩追问**，而且第 234 行的"可验证差异（同一任务跨多次会话时仍能返回完整上下文集合）"恰好就是这个主张的可检验形式。
