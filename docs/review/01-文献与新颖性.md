## 一、总体判断

**结论：文献部分"真实性基本达标、结构与新颖性不达标"，尚未达到开题要求，须实质性返修后方可提交。**

30 条文献逐条核验后，**29 条通过、1 条（[29] SUS 的页码）未核实、0 条伪造**：包括被列为高风险的两条《软件学报》2026 年中文文献（[11][12]）——已在期刊官网确认卷期、页码、DOI 与作者，ChatDev 的 ACL 2024 页码与 DOI、Barke 的 PACMPL 7(OOPSLA1):85-111、Parnin 的 SQJ 19(1):5-34 亦全部吻合，**不存在编造文献的问题**，这一点应明确写进答辩准备。

但**"研究空白"论断与创新点 1、3 的新颖性存在致命风险**：报告在"以任务为中心组织开发上下文""中断恢复"两个核心主张上，只与商业工具（会话式客户端、IDE 历史）对比，却漏掉了 Mylyn（FSE 2006）、TaskTracer（IUI 2005）、Codebook（ICSE 2010）、SZZ（MSR 2005）、Parnin & DeLine（CHI 2010）、Safer & Murphy（CASCON 2007）这一整条学术脉络；更严重的是，**这些工作就写在报告自己引用的 [20] 正文和参考文献表里**（已从原文 PDF 逐字提取核实），"只读二手综述正文、未顺其参考文献回溯"的痕迹非常明显，审稿人一眼可见。

此外，溯源部分只引了数据库溯源理论（Cheney），既未引 W3C PROV-O 标准，也未引 2025 年的 PROV-AGENT（已把 PROV 扩展到 AI agent 交互），使"缺少面向智能体过程的溯源模型"这一断言在 2025 年后**事实不成立**。文献数量与语种硬指标（≥30 篇、外文 ≥10 篇、近五年占较大比例）均达标，但灰文献占 20%、FSE/MSR/近三年 CHI 覆盖为 0，结构上偏"智能体能力 + 工具文档"，与人机交互侧的论证需要不匹配。

### 5.1 替换第 89 行（三（六）研究述评）整段

```text
本节五个小节可以归为三个方向：第（一）节对应"智能体能力"，回答能不能做；第（二）节对应"变更分析"，回答改了什么；第（三）（四）节分别从机器与人的角度回答"为什么需要证据"；第（五）节说明工程工具现状。

需要说明的是，"以任务为单位组织开发上下文"并非全新命题。Mylyn 早在 2006 年就提出任务上下文（task context）模型，并以任务聚焦界面按当前任务过滤 IDE 中的代码元素[31]；TaskTracer 在桌面层把文件、邮件与网页归集到任务[32]；Codebook 建立了代码实体与提交、缺陷、邮件之间的关联图[33]；SZZ 给出了"变更—问题"关联的经典算法[34]；Whyline[18] 与 noWorkflow[19] 示范了以证据链支撑"为什么"追问的交互方式；Parnin 与 Rugaber[20]、Parnin 与 DeLine[35] 以及 Safer 与 Murphy[36] 则给出了中断恢复的线索类型、实验证据与任务边界识别的界面研究。这些工作构成本课题的方法基础。

但它们共享一个前提：开发者直接在 IDE 或桌面中操作，任务由人显式声明或由窗口切换间接体现。当开发过程由代码智能体以自然语言指令驱动时，任务边界不再由用户显式激活，过程证据也从"编辑事件"变为"指令—工具调用—文件变更—测试运行"的异构序列；上述系统既没有面向智能体会话的事件模型，也没有把"验证依据"（测试）纳入证据链，更未处理跨会话的任务拼接与大模型生成摘要的可回溯约束。

因此，本文不主张"首次提出任务上下文"或"首次研究中断恢复"，而是：在智能体辅助开发这一新场景下，给出可落地的任务上下文与变更溯源表示，并对有效性做可测量的评估。就本文检索范围（2021—2026 年 ICSE、FSE、ASE、CHI、NeurIPS、ICLR、ICML、ACL 与《软件学报》）而言，尚未见到同时满足以下三点的系统：（1）以任务为根，统一挂接对话、变更、工具调用与测试四类记录；（2）变更粒度到 hunk，且支持"代码→原因→证据"与"对话/测试→受影响代码"双向查询；（3）在证据绑定约束下使用大模型生成任务摘要与关联候选。本课题即定位于此。
```

> 注意：改写后的"检索范围"是一句**可被检验的承诺**。作者必须真的按该式检索并留存检索记录（数据库、检索式、日期、命中数），否则仍属未证实断言。

### 5.2 替换第九章创新点 1

```text
1. **面向智能体会话的任务上下文重建。** 与 Mylyn[31] 等以"用户显式激活任务 + IDE 代码元素"为前提的任务聚焦界面不同，本系统面向代码智能体产生的事件流：在任务边界不被显式声明的情况下，依据空闲时长、目标切换、显式指令与提交动作判定任务边界，把跨多次会话的对话、变更、工具调用与测试统一挂接到同一任务之下，形成可查询的任务上下文图。可验证差异：给定同一任务的两次会话记录，系统能自动归并为同一任务并返回完整上下文集合，以任务边界判定 F1 ≥ 0.80 检验。
```

### 5.3 替换第九章创新点 3

```text
3. **面向智能体任务的恢复快照生成。** 已有研究已给出中断恢复的线索类型与恢复策略[20,35]，但恢复所需的信息仍需开发者自行搜集与拼接。本系统在此基础上，把恢复线索从"人工重建"转为"由任务上下文图自动生成"：以任务快照呈现已完成（有通过测试支撑的变更）、未完成（已提出未实施的计划）与待验证（失败或未运行的测试）三类事项，并支持从摘要直接跳转到证据。可验证差异：恢复用时与理解正确率相对"Git 日志 + 原始会话记录"基线的变化可被测量（报告效应量与 95% 置信区间）。
```

### 5.4 创新点 2 的补丁句（插在该条"相比 Git 只记录……"之后）

```text
需要区分的是：SZZ[34] 建立的是"变更—缺陷报告"的单向关联，Codebook[33] 建立的是"代码—沟通记录"的静态关联，二者都不包含"这次修改由哪句指令触发、由哪次测试验证"的证据链；本系统的差异在于以 hunk 为单位同时绑定触发消息、工具调用、测试运行与后续演化四类证据。
```

### 5.5 建议在 3.(四) 增补的一段（可直接粘贴）

```text
任务上下文与中断恢复是开发者工具研究的经典问题。Mylyn 以任务上下文模型驱动 IDE 的任务聚焦界面，按当前任务过滤代码元素并记录相关活动[31]；TaskTracer 在桌面层把文件、邮件与网页归集到任务[32]；ActivitySpace 进一步依据任务上下文在多个应用间推荐相关代码元素[38]。在恢复侧，Parnin 与 Rugaber 归纳了开发者中断后的恢复策略及其对线索丰富程度的依赖[20]，Parnin 与 DeLine 用实验比较了情景线索与语义线索的效果[35]，Safer 与 Murphy 则研究了任务边界识别界面[36]，Robbes 与 Lanza 刻画了开发会话的结构[37]。这些研究为本课题提供了设计依据，但其对象是"人在 IDE/桌面中的操作"，线索来源是编辑与窗口事件；当开发过程由智能体驱动时，可用线索变为指令、工具调用、文件变更与测试结果，恢复视图也必须从"重放操作历史"转为"按任务组织证据"。据我们所知，尚无工作把上述线索组织成面向智能体任务的可查询证据链并做恢复效果的量化评估，这是本课题的切入点。
```
